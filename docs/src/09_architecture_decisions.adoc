[[section-design-decisions]]
== Decisiones de arquitectura

Se documentan como ADR abreviados (contexto / decisión / consecuencias).
Las decisiones de mayor calado ya se resumieron en
<<section-solution-strategy>>; aquí se detallan con sus alternativas
consideradas.

=== ADR-1: Reducir el alcance a un MVP multiplataforma simple

*Contexto*: la propuesta original incluía correlación de identidades
entre Instagram, Twitter/X y Reddit mediante embeddings y clustering.

*Decisión*: MVP centrado en análisis por plataforma individual (Reddit,
luego Instagram), sin correlación cruzada.

*Consecuencias*: (+) alcance viable para un TFG; (+) evita la tensión
ética de comparar contra cuentas de terceros sin consentimiento;
(-) el módulo de correlación entre plataformas queda como trabajo
futuro, sin implementar.

=== ADR-2: Backend en Python (FastAPI) sobre el servicio Node heredado

*Contexto*: la plantilla universitaria (`yovi_en1b`) traía un servicio
`users` en Node/Express.

*Alternativas consideradas*: mantener Node y llamar a un
microservicio Python aparte solo para NLP; reescribir todo en Node
usando bindings de NLP menos maduros.

*Decisión*: sustituir el contenido de `users/` por Python/FastAPI
completo, conservando inicialmente la carpeta y la infraestructura
circundante; renombrada más adelante a `backend/` (ver ADR-7).

*Consecuencias*: (+) acceso directo al ecosistema NLP de Python
(spaCy, scikit-learn) sin llamadas entre servicios; (-) hubo que
reescribir el Dockerfile, los tests y adaptar el instrumentador de
métricas a un paquete distinto (`prometheus-fastapi-instrumentator`
frente a `express-prom-bundle`).

=== ADR-3: Sin persistencia (procesamiento 100% en memoria)

*Contexto*: cumplimiento RGPD y minimización de datos.

*Decisión*: ninguna base de datos; el único estado entre peticiones es
una cookie de sesión firmada con el `access_token`.

*Consecuencias*: (+) cerrar sesión elimina cualquier rastro del
usuario en el sistema; (+) simplifica drásticamente el argumentario
RGPD de la memoria; (-) no hay histórico de análisis previos ni
posibilidad de comparar la evolución del score en el tiempo (aceptado
como limitación conocida).

=== ADR-4: Modelo de datos genérico tras detectar acoplamiento a Reddit

*Contexto*: la primera integración de Instagram normalizaba su media
directamente al modelo `RedditPost`, reutilizando el campo `subreddit`
para el hashtag y forzando una arquitectura "Reddit como plataforma
principal, Instagram adaptándose a su modelo".

*Decisión*: refactor a `SocialPost`/`SocialProfile` con campos neutros
(`group`, `score`, `platform`), y unificación de la ruta de análisis a
`/api/analyze/{platform}` con un diccionario de factories.

*Consecuencias*: (+) añadir una plataforma nueva no requiere adaptar
modelos ajenos; (+) cobertura de tests más simétrica entre plataformas
(pasó de 84% a 93% al parejar los tests de Reddit con los ya existentes
de Instagram); (-) coste de refactor no trivial una vez el código ya
estaba en producción de pruebas.

=== ADR-5: Rechazo de verificación de integridad del lado del cliente

*Contexto*: al ser el código open source, se planteó proteger el flujo
OAuth con una comprobación de hash del código cliente antes de permitir
su ejecución.

*Decisión*: no implementar esa protección.

*Justificación*: en software open source, cualquier comprobación que
viva en el mismo código que se distribuye es evadible por quien
controla el entorno de ejecución (comentar la comprobación, recalcular
el hash esperado, ejecutar con depurador). El límite de confianza real
del sistema es el servidor de autorización OAuth de cada plataforma, no
el código propio: ninguna modificación del cliente permite obtener un
`access_token` sin el consentimiento explícito del titular de la cuenta
en la pantalla de la propia plataforma.

*Consecuencias*: (+) se evita invertir esfuerzo en una protección
inefectiva y fácilmente cuestionable ante un tribunal técnico; (+) la
memoria puede argumentar correctamente dónde está el verdadero límite
de confianza del sistema.

=== ADR-6: Rangos de versión en vez de versiones exactas

*Contexto*: varias roturas de entorno (numpy sin wheel para la versión
de Python del desarrollador, luego `pydantic_core`/`fastapi` con Python
3.14, y efectos en cadena sobre `respx` y
`prometheus-fastapi-instrumentator`).

*Decisión*: `requirements.txt`/`requirements-dev.txt` usan rangos
(`>=x,<y`) en vez de pines exactos.

*Consecuencias*: (+) resiliencia frente a distintas versiones de Python
entre máquinas de desarrollo y el runner de CI; (-) build ligeramente
menos determinista (dos instalaciones en momentos distintos pueden
resolver versiones exactas distintas dentro del rango).

=== ADR-7: Reutilización del monorepo de la asignatura ASW

*Contexto*: la plantilla `yovi_en1b` (Uniovi) ya traía Docker Compose,
Prometheus/Grafana, GitHub Actions y SonarCloud configurados.

*Decisión*: partir de ese repositorio, eliminando el servicio `gamey`
(Rust, ajeno al TFG) y sustituyendo el contenido de `users/` (antes
Node) por el backend Python. La carpeta se mantuvo con el nombre
heredado (`users/`) durante buena parte del desarrollo -- coste de
oportunidad aceptado frente a tocar Docker Compose, CI y SonarCloud
antes de que el resto del proyecto estuviera estable -- y se renombró a
`backend/` más adelante, actualizando esas mismas piezas de golpe.

*Consecuencias*: (+) ahorro significativo de tiempo de configuración de
infraestructura; (-) necesidad de mantener consistencia de convenciones
heredadas (nombres de servicios, puertos, estructura de carpetas) aunque
el dominio del proyecto no tenga relación con el original; (-) el
rename posterior tuvo que tocar simultáneamente `docker-compose.yml`, dos
workflows de GitHub Actions, `sonar-project.properties`, `.gitignore` y
la configuración de Prometheus -- todos los sitios que hacían referencia
literal a la carpeta por nombre, un recordatorio de que ese acoplamiento
disperso tiene coste real cuando llega el momento de deshacerlo.

=== ADR-8: Estimación de k-anonimato con proporciones agregadas del INE, no una base de datos sintética

*Contexto*: se necesitaba mostrar al usuario "cuánta gente comparte tus
características autodeclaradas" (edad, sexo, provincia, estudios...),
al estilo de una tabla de k-anonimato clásica.

*Alternativas consideradas*: construir una base de datos sintética con
una fila por cada uno de los ~49 millones de habitantes de España
(poblada a partir de Censo/Padrón/microdatos del INE) y resolver la
consulta con un `SELECT COUNT(*) ... WHERE ...` real.

*Decisión*: multiplicar en cadena proporciones agregadas del INE
(`data/ine_reference.py`), asumiendo independencia estadística entre
atributos, en vez de materializar microdatos sintéticos.

*Consecuencias*: (+) coherente con el principio "sin persistencia" que
sostiene el resto del argumentario RGPD del proyecto; (+) trivial de
auditar (cada número del informe se puede rastrear a una multiplicación
concreta); (+) no requiere procesar microdatos reales del INE (formato
de registro fijo, no trivial de tratar); (-) menos preciso que microdatos
reales en los casos donde hay correlación real entre atributos (p. ej.
la distribución de edad no es exactamente igual en todas las provincias)
— limitación documentada explícitamente en el propio informe.

=== ADR-9: Geolocalización de fotos limitada a España y a nivel de provincia

*Contexto*: se planteó geolocalizar fotos de Instagram al estilo de
herramientas comerciales tipo GeoSpy.

*Alternativas consideradas*: replicar un índice de geolocalización
mundial (inviable: requiere cientos de millones de imágenes
georreferenciadas e infraestructura fuera del alcance de un TFG);
predecir coordenadas GPS exactas (poco realista: incluso el estado del
arte publicado solo acierta la calle/1km ~26-29% de las veces).

*Decisión*: DINOv2 (extracción de embeddings) + FAISS (búsqueda de
vecinos más cercanos) contra un índice construido únicamente con
imágenes de España (subconjunto filtrado del dataset público OSV-5M), y
la predicción se agrega a nivel de **provincia** cuando es posible; si
solo se puede identificar la comunidad autónoma (varias provincias
posibles, sin forma honesta de elegir una) se usa ese nivel intermedio en
vez de forzar una provincia concreta o perder el dato por completo -- ver
ADR-16 para los requisitos de consenso antes de aceptar cualquiera de los
dos niveles como residencia habitual.

*Consecuencias*: (+) índice manejable en recursos de un TFG (varios GB
en vez de un dataset mundial); (+) mayor precisión relativa al competir
en un espacio de búsqueda más pequeño; (+) la granularidad de provincia
(o comunidad autónoma, cuando aplica) coincide con la que ya usa el
módulo de k-anonimato, integrándose de forma natural en el resto del
informe; (-) no compite en precisión con herramientas comerciales que sí
tienen infraestructura e índices mundiales propietarios — limitación
reconocida y documentada, no ocultada.

=== ADR-10: Mistral AI como proveedor de análisis con IA, por jurisdicción

*Contexto*: se quería una función opcional para que un LLM leyera el
informe ya generado y diera conclusiones en lenguaje natural. Se
valoraron varios proveedores baratos, incluido DeepSeek.

*Alternativas consideradas*: DeepSeek (más barato, pero empresa china:
implica una transferencia internacional de datos personales fuera del
Espacio Económico Europeo, con las obligaciones adicionales del RGPD
Capítulo V que eso conlleva); modelo propio entrenado/fine-tuned
localmente (descartado: coste de entrenamiento y de generación de
dataset desproporcionado para una tarea de razonamiento en contexto
sobre datos ya estructurados, que no requiere especialización de
dominio).

*Decisión*: Mistral AI (La Plateforme), tier gratuito, empresa con sede
en Francia.

*Consecuencias*: (+) evita justificar una transferencia internacional de
datos personales, al procesarse dentro de la UE; (+) sin coste (tier
gratuito, con degradación explícita si se agota la cuota, sin
reintentos); (-) calidad de respuesta algo menor que la de modelos de
proveedores más caros según benchmarks públicos, aceptado como
compromiso razonable para una función complementaria opcional.

*Nota*: este mismo razonamiento de jurisdicción aplicó también, sin
volver a discutirlo desde cero, cuando se añadió una segunda integración
independiente con el mismo proveedor (`nlp/ai_attribute_extraction.py`,
ver ADR-13) que envía texto/bio públicos en vez de un informe ya
agregado.

=== ADR-11: Progreso en vivo vía Server-Sent Events, no polling ni WebSockets

*Contexto*: el análisis completo (sobre todo con geolocalización de
fotos activada) puede tardar varios segundos; se quería sustituir la
espera opaca por una pantalla de progreso real.

*Alternativas consideradas*: *polling* periódico desde el frontend
(añade latencia y carga innecesaria); WebSockets (bidireccional,
más complejo de lo que este caso de uso necesita, ya que el servidor
nunca necesita recibir datos del cliente durante el análisis).

*Decisión*: Server-Sent Events (`GET /api/analyze/{platform}/stream`),
unidireccional servidor->cliente, con eventos JSON (`{"done": false,
"stage": "...", ...}` en curso, `{"done": true, "report": {...}}` o
`{"done": true, "error": "..."}` al terminar). El endpoint clásico
(`POST /api/analyze/{platform}`) se mantiene sin cambios para
compatibilidad y para los tests existentes.

*Consecuencias*: (+) hitos de progreso REALES (cada evento corresponde a
un paso del pipeline que de verdad acaba de terminar, no a un
temporizador simulado); (+) más simple de implementar y depurar que
WebSockets para un flujo unidireccional; (-) dos endpoints distintos
para la misma lógica de negocio (`_build_report` compartido entre
ambos, para no duplicar la orquestación).

=== ADR-12: Webapp y backend bajo el mismo origen (proxy de Nginx), en vez de `VITE_API_URL` absoluto

*Contexto*: en desarrollo local con un túnel rápido de Cloudflare
(`trycloudflare.com`, gratuito) para poder probar el login de Instagram
(que exige `redirect_uri` HTTPS), la webapp y el backend vivían en
dominios distintos. Cada reinicio del túnel generaba una URL nueva que
había que propagar manualmente a tres sitios: `INSTAGRAM_REDIRECT_URI`,
el panel de Meta for Developers, y `VITE_API_URL` de la webapp.

*Alternativas consideradas*: automatizar la propagación de la URL nueva
con un script que reescribiera `.env` y reconstruyera la webapp en cada
reinicio del túnel (descartado: sigue exigiendo un paso manual en Meta,
que no tiene API para gestionar su lista de redirect URIs válidos, así
que la automatización no eliminaba el cuello de botella real, solo lo
desplazaba); usar un túnel con nombre/persistente de Cloudflare
(descartado por el momento: exige un dominio propio en Cloudflare, fuera
del alcance gratuito del proyecto).

*Decisión*: servir la webapp y el backend bajo un único origen. El
Nginx de la imagen de la webapp hace de proxy inverso hacia el backend
(`/auth/*`, `/api/*`) bajo el mismo dominio de cara al navegador; la
webapp se construye con `VITE_API_URL` vacío (rutas relativas). El
`redirect_uri` de Instagram y el destino de la redirección final tras el
login se derivan del header `Host` de la petición entrante cuando no hay
un valor fijo en `.env` (`auth/dynamic_origin.py`).

*Consecuencias*: (+) un único túnel apuntando al puerto de la webapp
sirve también, transparentemente, la autenticación y la API; (+) solo
queda un paso manual (dar de alta la URL en Meta), no tres sitios que
sincronizar; (+) el mismo mecanismo simplifica también producción (ya no
hace falta un `DEPLOY_HOST` para construir la imagen de la webapp,
Docker resuelve `backend` por DNS interno igual en local que
desplegado); (-) la derivación dinámica solo es correcta cuando webapp y
backend comparten origen de verdad -- documentado explícitamente para no
asumir por error que sirve también para desarrollo sin Docker con
puertos distintos (`npm run dev` + `uvicorn` sueltos).

=== ADR-13: Extracción de atributos con IA como complemento de las regex, nunca sustituto

*Contexto*: las regex de `demographic_extraction.py` tienen un
vocabulario fijo ("estudio X", "estudiante de X"...); cualquier
redacción real que no encaje se pierde en silencio (p. ej. "voy a 2º de
Enfermería").

*Alternativas consideradas*: sustituir las regex por extracción vía IA
por completo (descartado: perdería la garantía de coincidencia exacta y
determinista que ya funcionaba bien, y encarecería/ralentizaría el
análisis incluso para los casos que las regex ya resolvían gratis);
pedir a la IA que decidiera directamente la categoría del INE
correspondiente (descartado: una alucinación del modelo podría colar una
categoría inventada como si fuera una estimación de población real).

*Decisión*: `nlp/ai_attribute_extraction.py` corre siempre después de
las regex y solo rellena los campos que estas no encontraron
(`merge_findings`, con las regex teniendo prioridad). El LLM solo
propone texto libre; la normalización final contra las tablas del INE
la sigue haciendo el propio código, igual que para las regex. Además,
propone por separado una estimación de sexo por convención cultural del
nombre público de la cuenta, marcada con una procedencia distinta
(`ia_nombre`) y una nota de menor fiabilidad explícita en el informe --
nunca se mezcla con una autodeclaración real en el mismo nivel de
confianza.

*Consecuencias*: (+) capta redacciones libres sin perder la
trazabilidad ni la resistencia a alucinaciones del enfoque por regex;
(+) coherente con el principio de explicabilidad del resto del proyecto
(ver <<section-concepts>>); (-) el análisis ahora depende, para esta
mejora concreta, de una llamada de red adicional a un tercero (Mistral),
mitigado por ser opcional y degradarse con gracia sin `MISTRAL_API_KEY`.

=== ADR-14: Análisis del informe con IA disparado automáticamente, no bajo demanda

*Contexto*: la primera versión exigía que el usuario pulsara
explícitamente "Analizar con IA" tras ver el informe.

*Decisión*: se dispara solo, en cuanto el informe principal está
disponible, sin confirmación adicional del usuario.

*Justificación*: el consentimiento OAuth inicial ya cubre todo el
análisis que la herramienta hace sobre la cuenta del usuario; un botón
adicional para una llamada que solo envía agregados ya generados (nunca
las publicaciones originales) no añadía ninguna protección de privacidad
real, solo fricción de interfaz. La función sigue siendo aislada y
opcional en caso de fallo (sin `MISTRAL_API_KEY`, o si Mistral no
responde, el resto del informe no se ve afectado) -- lo único que
cambió es cuándo se dispara, no las garantías de degradación.

*Consecuencias*: (+) el usuario ve el veredicto y las conclusiones sin
un paso extra; (-) una llamada más a Mistral en cada análisis (incluso
si el usuario no llega a mirar esa sección), aceptado por ser
gratuita/de bajo coste y por degradarse sin romper nada si falla.

=== ADR-15: Dependencias de geolocalización activables por build-arg, con precarga en el arranque

*Contexto*: `torch`/`faiss`/`transformers` no estaban en
`requirements.txt` bajo la premisa de que "solo hacen falta para
construir el índice" (un script que se corre aparte, no en el backend
desplegado). Esa premisa resultó ser incorrecta: el propio análisis en
producción también necesita esas librerías para calcular el embedding de
cada foto del usuario y consultar el índice ya construido -- sin ellas
en la imagen del backend, la función se reporta como "no disponible"
aunque el índice exista y esté montado correctamente.

*Alternativas consideradas*: instalarlas siempre en `requirements.txt`
(descartado por defecto: cientos de MB extra en instalaciones que no
usan Instagram o no quieren geolocalización); mantener el bug
implícitamente y limitarse a documentar "esta función requiere pasos
adicionales que no automatizamos" (descartado: no es coherente con el
resto del proyecto, que sí tiene la ambición de que los módulos
opcionales se activen limpiamente).

*Decisión*: `requirements-vision.txt` aparte, instalado en la imagen
Docker solo si se construye con `--build-arg WITH_GEOLOCATION=true`
(activado por defecto en `docker-compose.yml`), usando el índice de
PyTorch solo-CPU (más ligero que el paquete de PyPI por defecto, que
incluye CUDA). El modelo y el índice se precargan en el `lifespan` de
FastAPI al arrancar el contenedor, no en la primera petición de
análisis, y la caché de los pesos del modelo se persiste en un volumen
para no volver a descargarlos en cada reinicio.

*Consecuencias*: (+) instalaciones sin geolocalización siguen siendo
ligeras; (+) el primer usuario en analizar una cuenta de Instagram tras
un despliegue no paga el coste de cargar el modelo; (+) el modelo no se
vuelve a descargar en cada reinicio del contenedor; (-) activar
geolocalización añade varios minutos a la primera construcción de la
imagen (descarga de `torch`), mitigado con timeouts/reintentos más
generosos en `pip` para conexiones lentas.

=== ADR-16: Consenso entre varias fotos, y exclusión de fotos de viaje, antes de asumir residencia por imagen

*Contexto*: la primera versión aceptaba la conclusión de residencia con
una sola foto por encima de un umbral de confianza bajo (40%). En la
práctica esto era demasiado permisivo para un dato tan sensible: (a) una
sola foto genérica (solo mar, solo cielo, un primer plano sin fondo
distintivo) puede coincidir por casualidad con un umbral bajo sin que el
contenido diga nada real sobre dónde vive la persona, y (b) una foto de
vacaciones/viaje con confianza alta indica dónde ESTUVO la persona en ese
momento, no dónde VIVE.

*Alternativas consideradas*: mantener un único umbral fijo más alto para
una sola foto (más simple, pero sigue sin distinguir "una foto puntual
casualmente segura" de "señal real y repetida"); pedir confirmación
manual al usuario antes de aceptar una ubicación por imagen (más preciso,
pero rompe el flujo 100% automático del resto del análisis y añade
fricción de UI fuera del alcance de este TFG).

*Decisión*: exigir consenso entre varias fotos de la MISMA comunidad
autónoma antes de aceptar una conclusión de residencia: al menos 2 fotos
con más del 80% de confianza, o al menos 4 con más del 60%
(`HIGH_CONFIDENCE*`/`MODERATE_CONFIDENCE*` en `report/generator.py`).
Antes de contar, se excluyen las fotos marcadas como "de viaje"
(detectadas por regex en `nlp/travel_detection.py` y, en el mismo pase,
por IA vía el campo `fotos_de_viaje` del prompt de
`ai_attribute_extraction.py` -- las dos fuentes se UNEN, nunca se
sustituyen) y las marcadas como no representativas por
`vision/geolocation.py` (vecinos más parecidos geográficamente
dispersos, ver ADR-9).

*Consecuencias*: (+) reduce sustancialmente los falsos positivos de
residencia por imagen, el tipo de error más dañino en una herramienta que
se presenta como educativa/defensiva; (+) las fotos de viaje dejan de
contaminar la conclusión, incluso con confianza de geolocalización
altísima; (-) los umbrales concretos (2/80%, 4/60%) son una primera
propuesta razonable, no una cifra derivada de un estudio -- quedan como
constantes explícitas y fácilmente ajustables si en la práctica resultan
demasiado (o poco) exigentes, en vez de un "número mágico" enterrado en
la lógica; (-) cuentas con pocas fotos de Instagram probablemente nunca
alcancen el consenso necesario, así que la geolocalización por imagen se
queda sin usarse en la práctica para esos casos -- comportamiento
correcto y esperado (mejor "no estimable" que una conclusión poco
fiable), no un fallo.

=== ADR-17: Moondream2 local para analizar el contenido de las fotos, en vez de Mistral Pixtral

*Contexto*: se quería, además de geolocalizar cada foto, extraer señales
sobre su contenido (aficiones, actividades, señal de pareja). El resto de
funciones de IA del proyecto usan Mistral AI (ver ADR-10), que sí ofrece
un modelo multimodal (Pixtral) capaz de analizar imágenes.

*Alternativas consideradas*: Mistral Pixtral vía API, igual que el resto
de integraciones de IA del proyecto (coherente con ADR-10, un único
proveedor); un modelo de clasificación de imágenes clásico entrenado a
medida (descartado: requeriría un dataset etiquetado de aficiones/
actividades que no existe, desproporcionado para el alcance de un TFG).

*Decisión*: Moondream2, un modelo de visión-lenguaje (VQA) pequeño
(~1.8B parámetros) ejecutado localmente vía `transformers`, con el mismo
patrón de dependencia opcional que ya usa `geolocation.py`
(`requirements-vision.txt`, `--build-arg WITH_GEOLOCATION=true`).

*Justificación*: a diferencia de las otras dos integraciones con Mistral
(`ai_analysis.py` sobre el informe ya agregado, `ai_attribute_extraction.py`
sobre texto/bio), este análisis necesita una llamada POR FOTO, no una por
informe -- una cuenta con varias decenas de fotos analizadas agotaría el
tier gratuito de Mistral en un único análisis. Un modelo local, en
cambio, no tiene límite de peticiones por minuto una vez cargado, y
además mantiene la imagen dentro del propio servidor en vez de enviarla a
un tercero -- coherente con el principio de minimización de datos del
resto del proyecto (aunque las fotos de Instagram sean públicas, seguir
minimizando dónde viajan sigue siendo la postura por defecto de este
proyecto).

*Consecuencias*: (+) sin límite de tasa por foto, ni coste por llamada;
(+) la imagen no sale del servidor; (+) reutiliza el mismo patrón de
dependencia opcional, build-arg y degradación que ya existía para
`geolocation.py`, sin inventar uno nuevo; (-) modelo bastante menos capaz
que Pixtral en tareas VQA abiertas, mitigado limitando la tarea a una
pregunta cerrada de formato fijo en vez de una descripción libre; (-)
Moondream2 se carga con `trust_remote_code=True` (código Python propio
del modelo, no solo pesos) -- superficie de confianza real que merece
mencionarse explícitamente en la memoria, aunque el modelo y su revisión
(`_MODEL_REVISION`, fijada explícitamente en el código) provengan de un
repositorio público de Hugging Face con uso extendido; (-) no se precarga
en el arranque del contenedor como el modelo de geolocalización (ver
ADR-15), así que la primera foto de cada proceso paga el coste de carga.

=== ADR-18: Rechazo de reconocimiento facial y de clasificación de rasgos físicos/étnicos

*Contexto*: se planteó ampliar `vision/scene_analysis.py` para que,
además de escena/objetos/aficiones/indicios de pareja (ver ADR-16 y el
prompt del módulo), extrajera también color de piel, pelo y ojos de las
personas que aparecen en las fotos, como señal adicional para acotar el
k-anonimato -- misma lógica ya aplicada a atributos autodeclarados en
texto. Junto con esto, se planteó identificar cuál de las personas de
cada foto es la propia cuenta analizada, comparando contra la foto de
perfil o, en su defecto, localizando a la persona que más se repite a lo
largo de las publicaciones.

*Alternativas consideradas*: implementarlo igualmente, apoyándose en que
los embeddings faciales necesarios no se persisten (coherente en
apariencia con ADR-3) y en que la intención es defensiva/educativa,
justo como el resto del proyecto.

*Decisión*: no implementar ninguna de las dos cosas. `scene_analysis.py`
se mantiene deliberadamente acotado a objetos/escena/aficiones/indicios
de pareja -- nunca a la descripción física de las personas que aparecen
ni a su identificación entre fotos.

*Justificación*: a diferencia de otras decisiones de alcance de este
proyecto, esta no es solo una cuestión de prudencia o de coste/beneficio
para un TFG -- tiene dos problemas de fondo independientes entre sí:

- *Categoría especial de datos (art. 9.1 RGPD)*: color de piel, pelo y
  ojos usados con fin de acotar/identificar encajan como datos relativos
  al origen racial/étnico y datos biométricos. El consentimiento OAuth de
  este proyecto cubre que el usuario analice su propia actividad pública,
  pero no constituye base legal para que el sistema clasifique rasgos
  raciales o biométricos de nadie con ese fin -- es exactamente el tipo
  de tratamiento que el RGPD trata con más cautela, no menos. Y el
  argumento de "no se persiste" (que sí es válido para justificar ADR-3)
  no se traslada aquí: el art. 4.2 define "tratamiento" como cualquier
  operación sobre datos personales, automatizada o no, *se persista o no
  el resultado*. Que un embedding facial se calcule solo en memoria y se
  descarte al momento no cambia que el tratamiento de un dato de
  categoría especial ya ocurrió.
- *Terceros sin consentimiento*: determinar "cuál de las personas de la
  foto es el usuario" -- ya sea por comparación con la foto de perfil o
  por frecuencia de aparición -- exige procesar la cara de **todas** las
  personas presentes en cada foto para poder distinguir/descartar, no
  solo la del usuario: detección de rostro + embedding + comparación o
  clustering entre fotos, es decir, reconocimiento facial de terceros
  (acompañantes, amigos, desconocidos de fondo) que nunca dieron su
  consentimiento vía OAuth ni de ninguna otra forma. El consentimiento
  del titular de la cuenta -- la pieza que sostiene el argumentario RGPD
  de todo el resto del proyecto (ver ADR-5) -- no se extiende a las demás
  personas que aparecen en su contenido.

Como razón adicional, ya de calidad de la señal y no de legalidad: los
VLM son conocidos por ser poco fiables e inconsistentes clasificando
tono de piel (varía con iluminación, balance de blancos, ángulo de la
cámara), así que alimentar esa señal al k-anonimato daría una falsa
sensación de precisión sobre una estimación ya de por sí aproximada (ver
ADR-8).

*Consecuencias*: (+) el argumentario RGPD del proyecto se mantiene
consistente en toda la memoria, sin una excepción que lo contradiga
justo en el módulo pensado para concienciar sobre exposición de datos;
(+) evita el riesgo reputacional y legal de distribuir, aunque sea como
TFG, una herramienta que haga perfilado racial o reconocimiento facial de
terceros sin su consentimiento; (-) el k-anonimato por imagen se queda
sin una señal que, en la práctica, sí podría acotar algo más la
población estimada -- aceptado como límite de alcance, igual que la
correlación entre plataformas en ADR-1.

=== ADR-19: bfloat16 inutilizable en CPU sin aceleración por hardware -- float32 forzado, cuantización descartada

*Contexto*: Moondream2 (ADR-16) se descarga con el dtype con el que
Hugging Face publica sus pesos, `bfloat16`, sin que el código de este
proyecto pase ningún `dtype` explícito a `from_pretrained()` (ver
historial de bugs nº1-4 en el docstring de `_lazy_load()` en
`scene_analysis.py`: cualquier kwarg de dispositivo/dtype disparaba un
error de "meta tensor" propio de cómo `accelerate` inicializa modelos
con `trust_remote_code=True`). En una GPU con tensor cores esto es lo
correcto. En CPU de consumo (sin instrucciones AVX-512 BF16, que solo
traen CPUs de servidor recientes) no hay aceleración de hardware para
`bfloat16` y PyTorch lo emula por software -- medido en producción:
*más de 3 horas* para analizar una sola foto en un portátil de 8GB de
RAM sin GPU dedicada, frente a segundos en `float32` sobre la misma CPU.

*Alternativas consideradas*, todas probadas con evidencia real, no solo
en teoría, antes de llegar a la solución final:

- *Cuantización dinámica int8 de PyTorch* (`torch.quantization.quantize_dynamic`):
  Moondream2 no usa `nn.Linear` para casi ninguna capa interna -- la
  atención y el MLP usan una `@dataclass` propia del modelo
  (`LinearWeights`, ver `layers.py` del código remoto) con una función
  `linear()` que llama a `F.linear()` a mano sobre los tensores sueltos,
  en vez de invocar el módulo de la forma estándar de PyTorch
  (`modulo(x)`). `quantize_dynamic` solo sabe sustituir instancias reales
  de `nn.Linear`, así que solo llega a tocar `patch_emb` (la única capa
  de ese tipo) -- el resto de la red, que es la inmensa mayoría de los
  parámetros, queda intacta. Descartada: no aporta beneficio real de
  memoria ni velocidad proporcional al riesgo de tocar internals del
  modelo.
- *Cuantización int4 nativa del propio modelo* (clase `QuantizedLinear`
  en el código remoto, vía `torchao.quantization.int4_weight_only`):
  termina su rutina de carga con `torch.cuda.empty_cache()` -- pensada
  explícitamente para GPU/CUDA. Descartada para despliegue en CPU.
- *float32 completo*: correcto y rápido en CPU (sin emulación), pero
  ronda 1.9B parámetros × 4 bytes ≈ 7.6GB solo para los pesos del
  modelo -- inviable en una máquina con 8GB de RAM totales junto al
  resto del stack (Grafana, el propio backend, DINOv2). *Aceptada* como
  la vía correcta en cuanto a corrección numérica, condicionada a tener
  suficiente RAM disponible (ver Consecuencias).

*Decisión*: cargar siempre en `bfloat16` primero (sigue siendo la forma
oficial y estable de cargar el modelo, ver ADR-16), y convertir después
a `float32` parámetro a parámetro (`param.data = param.data.float()`),
nunca con `_model.to(dtype=torch.float32)` sobre el módulo completo --
esa llamada es la que dispara el mismo error de "meta tensor" que ya
bloqueó los intentos nº2 y nº4 del historial de `_lazy_load()`. Esta
conversión se hace *solo si no hay GPU disponible*
(`_upcast_to_float32_if_cpu()` en `scene_analysis.py`): en GPU,
`bfloat16` ya está acelerado por hardware y forzar `float32` ahí
duplicaría el uso de VRAM sin ninguna ganancia.

Además, como la conversión por `parameters()`/`buffers()` no alcanza a
las capas basadas en `LinearWeights`/`LayerNormWeights` (no están
registradas como tal en el árbol de módulos de PyTorch, ver docstring de
`_upcast_to_float32_if_cpu()`), se añade un recorrido adicional buscando
cualquier `@dataclass` colgada como atributo de un submódulo con campos
`torch.Tensor` en `bfloat16`. Y como la imagen de entrada llega en
`bfloat16` a fuego (`prepare_crops()` en el código remoto lo fija sin
mirar el dtype del modelo, y parchear esa función por nombre no tuvo
efecto en las pruebas realizadas, por una razón no identificada), se
intercepta directamente el `forward` del submódulo `patch_emb`
(localizado por búsqueda en `named_modules()`, no por ruta de atributo
fija) para forzar el cast justo antes de usarlo.

*Justificación*: entre las alternativas investigadas, `float32` es la
única que preserva la arquitectura del modelo sin parches quirúrgicos
en capas internas (a diferencia de la cuantización int8, que solo cubre
una capa de cientos) y sin depender de hardware que este proyecto no
puede asumir que el usuario tenga (a diferencia del int4 nativo, atado a
CUDA). El coste de memoria es real y explícito, no oculto: por eso
`enable_scene_analysis` (ver `config.py`) sigue desactivado por defecto,
en vez de asumir que toda máquina donde se despliegue este proyecto
tiene RAM de sobra.

*Consecuencias*: (+) cuando hay RAM suficiente (~10-12GB libres o más,
o cualquier GPU), el análisis de contenido pasa de horas a segundos por
foto, sin tocar la calidad de las respuestas del modelo (no es una
aproximación con pérdida como la cuantización, es la misma precisión
numérica con la que se entrenó); (+) la degradación sigue siendo
elegante si no se activa: `_SCENE_ANALYSIS_TIMEOUT_SECONDS` (ver
`geolocation.py`) sigue cortando a los 30s si algo va mal, sin bloquear
la geolocalización de la misma foto; (-) el análisis de contenido sigue
sin ser viable en portátiles modestos (8GB de RAM, sin GPU) -- limitación
de hardware real, no de este proyecto, documentada aquí en vez de
perseguida indefinidamente con más parches; (-) esta solución no se ha
podido validar en un análisis completo de principio a fin en ninguna
máquina real durante el desarrollo (el único entorno de prueba
disponible se quedó sin memoria antes de completar una inferencia) --
las piezas por separado (carga en float32, `patch_emb` con entrada
correcta) sí se verificaron una a una, pero queda pendiente una prueba
end-to-end en una máquina con RAM suficiente antes de dar esto por
completamente cerrado.

=== ADR-20: Concurrencia de fotos autocalibrada por máquina, con log de rendimiento propio en vez de ajuste manual a ciegas

*Contexto*: `Settings.photo_analysis_concurrency` (nº de fotos analizadas
en paralelo con DINOv2/Moondream2, ver ADR-15) era un entero fijo (`2`)
igual en cualquier máquina donde se desplegara el backend, elegido sin
ninguna medición real -- un servidor con muchos más núcleos que el
entorno de desarrollo se quedaría con el mismo valor, infrautilizando
la CPU disponible, y no había ningún dato (más allá de la percepción
subjetiva al usar la aplicación) con el que justificar un valor distinto
en la memoria del TFG.

*Alternativas consideradas*: dejar el valor fijo y documentar
"ajustar manualmente según la máquina" (descartado: exactamente lo que
se quería evitar, un paso manual más que además nadie sabría a qué
número mover sin medir antes); autoajuste dinámico dentro de un mismo
proceso, probando varias concurrencias y quedándose con la mejor
(descartado: no hay forma fiable de medir varias configuraciones sobre
el mismo lote de fotos sin repetir trabajo y con medidas ruidosas por
una sola muestra -- un verdadero óptimo requiere comparar análisis
completos, no improvisar dentro de uno).

*Decisión*: dos cambios independientes.

1. `photo_analysis_concurrency` pasa a autocalcularse en cada arranque a
partir de `os.cpu_count()` (`cpu_count // 2`, ver
`_default_photo_analysis_concurrency()` en `config.py`), sin tocar nada
al cambiar de servidor. Sigue siendo sobreescribible con la variable de
entorno `PHOTO_ANALYSIS_CONCURRENCY` para forzar un valor concreto (p.
ej. al comparar configuraciones a propósito); dejarla vacía en `.env`
se trata igual que no definirla (un `field_validator` intercepta la
cadena vacía antes de que Pydantic intente convertirla a `int`, que
si no se hubiera añadido, habría impedido arrancar la aplicación).
Además, la concurrencia *real* usada en cada análisis se capa al nº de
fotos de ese análisis concreto (`min(configured_concurrency, total)`,
en `geolocation.py`) -- nunca abre más huecos de paralelismo de los que
hay fotos que procesar.

2. Dos logs JSON Lines nuevos, en `backend/data/performance/` (ya
cubierto por el `.gitignore` de `backend/data/`, igual criterio que el
índice FAISS: regenerable, no versionado):
+
--
- `photo_analysis_log.jsonl` (`app/performance_log.py`): una línea por
  análisis con fotos -- núcleos, concurrencia configurada/real, hilos
  por inferencia, si Moondream2 estaba activo, y el tiempo de cada foto
  individual.
- `analysis_run_log.jsonl` (`app/analysis_run_log.py`): una línea por
  análisis completo (Reddit o Instagram) -- nº de posts/comentarios/
  fotos, y cuánto tardó cada etapa del pipeline (huella de escritura,
  detección de atributos, autodeclaraciones con IA, espera de la
  geolocalización en segundo plano, estrechamiento de población...). El
  desglose por etapa se recoge con `app/analysis_timing.py`, un
  `ContextVar` que cualquier función puede usar (`async with
  timed_stage("nombre"):`) sin que haya que añadir un parámetro nuevo a
  cada firma del pipeline (`generate_report`, `_apply_ai_findings`...).
  La tarea de geolocalización en segundo plano (ver ADR-15) se crea
  *antes* de activar este cronómetro a propósito, para que su tiempo
  siga midiéndose aparte, por foto, en el log anterior, y no se mezcle
  con el del pipeline principal.
--
+
Ambos logs son estrictamente técnicos: ningún campo identifica a la
persona ni a su cuenta (ni username, ni bio, ni permalinks, ni IP, ni
contenido de ningún post), coherente con ADR-3 (sin persistencia) -- no
son la base de datos que ese ADR evita, son observabilidad de
rendimiento. Ambos se desactivan juntos con
`ENABLE_PERFORMANCE_LOGGING=false` (activado por defecto) y nunca
lanzan una excepción hacia el análisis real: un fallo al escribir a
disco se registra como aviso una vez por proceso y se sigue sin
interrumpir nada.

Para analizarlos: `scripts/analyze_performance_log.py` (rendimiento por
foto, agrupado por configuración de núcleos/concurrencia) y
`scripts/analyze_analysis_run_log.py` (tiempo por etapa del pipeline
completo, con correlación simple frente al volumen de posts/fotos), los
dos con `pandas` y un modo `--plot` opcional.

*Justificación*: la autocalibración resuelve el problema práctico (no
hay que tocar nada al desplegar en otra máquina) sin fingir encontrar un
óptimo que solo se puede conocer midiendo. Los logs son precisamente esa
medición: en vez de defender la heurística por argumento, la memoria del
TFG puede apoyarse en cifras reales de segundos por foto y por etapa, en
distintas máquinas y configuraciones, acumuladas sin esfuerzo adicional
durante el uso normal de la aplicación.

*Consecuencias*: (+) cero pasos manuales al cambiar de servidor; (+)
datos empíricos citables para la sección "Plan de evaluación pendiente"
de la memoria, que antes no existían; (+) visibilidad de qué etapa del
pipeline pesa más en la práctica, no solo la de fotos (p. ej. permite
comprobar si `espera_geolocalizacion_fotos` tiende a cero, señal de que
el paralelismo con la tarea en segundo plano funciona de verdad, en la
línea de lo ya detectado en ADR-11 y en el historial de este proyecto
sobre paralelismo nominal vs. real); (-) la heurística
(`cpu_count // 2`) sigue siendo un punto de partida razonado, no un
óptimo demostrado -- validarlo (o ajustarlo) con los datos acumulados
queda como trabajo futuro, una vez haya suficientes análisis registrados
en máquinas distintas; (-) dos ficheros más creciendo sin límite en
`backend/data/performance/` mientras el proceso esté en marcha con el
logging activado -- sin rotación ni purga automática por ahora, asumible
para el volumen de análisis de un TFG pero a revisar si esto se
convirtiera en un despliegue de uso continuado.

=== ADR-21: Prompt de Moondream2 dividido en dos llamadas (caption en inglés + estructurado en español)

*Contexto*: el prompt original de `scene_analysis.py` combinaba un campo
de descripción general (DESCRIPCION) y tres campos de opciones fijas
(PERSONAS/AFICION/PAREJA) en una única llamada a `_model.query()`, con
placeholders `<explicación entre corchetes>` inline en la misma línea que
cada etiqueta. Probado con hardware real (GTX 1650) esto falló de dos
formas distintas, ambas confirmadas con la respuesta cruda del modelo, no
solo sospechadas:

1. El modelo devolvía literalmente el texto del placeholder como si fuera
la respuesta ("AFICION: una actividad, deporte, instrumento musical...")
en vez de sustituirlo por un valor real -- fallo de instruction-following
típico de un VQA de ~1.8B cuando la etiqueta, la explicación de las
opciones y el valor esperado se mezclan en la misma línea.
2. Corregido lo anterior (separando un ejemplo literal de líneas de la
explicación de qué valores son válidos, en párrafos aparte), el campo de
texto libre (DESCRIPCION) seguía fallando: el modelo copiaba literalmente
la frase de ejemplo dada ("varias personas charlando alrededor de una
mesa"), y en un caso la repitió una segunda vez tras terminar las otras
tres líneas. Investigado el porqué: el propio autor del modelo confirma
en la discusión "OCR and multi-Language support?" de
`huggingface.co/vikhyatk/moondream2/discussions/22` que *"the training
data is currently english-only"* -- pedirle generar una frase libre en
ESPAÑOL lo sacaba de su dominio de entrenamiento, produciendo gramática
rota y palabras inventadas (p. ej. "comengan", que no existe).

*Alternativas consideradas*: seguir puliendo el prompt español (varios
intentos reales, cada uno con fallos nuevos: ejemplos más cortos, más
énfasis en "sé concreto", listas de ejemplos enumerados -- estos últimos
acabaron literalmente citados en la respuesta, ver docstring de
`_CAPTION_QUERY`); traducir el caption con Mistral tras generarlo en
inglés (descartado: reintroduciría el mismo límite de tasa del tier
gratuito de Mistral que motivó pasar a un modelo local en primer lugar,
ver ADR-17, salvo que se batchee a una llamada por informe en vez de por
foto -- no implementado).

*Decisión*: separar en DOS llamadas independientes a `_model.query()`,
reutilizando la misma imagen ya codificada
(`_model.encode_image()`, ver ADR-22 para el porqué de codificar una
copia redimensionada, no la original):

- `_CAPTION_QUERY` (inglés): una única pregunta de texto libre, sin
  plantilla ni ejemplo de contenido que copiar -- solo una instrucción
  directa ("Describe what's happening..."), que es además el uso para el
  que Moondream2 está pensado (VQA/captioning de una sola pregunta, no un
  formato estructurado de varios campos). El caption resultante se
  muestra tal cual, EN INGLÉS, en vez de traducirse -- única excepción de
  idioma en un proyecto por lo demás en español, documentada
  explícitamente en el código para que no se confunda con un descuido.
- `_STRUCTURED_QUERY` (español): PERSONAS/AFICION/PAREJA/TEXTO_VISIBLE
  (ver ADR-23), formato de tres... ahora cuatro líneas fijas con ejemplo
  literal -- aquí SÍ funciona el ejemplo porque las respuestas son
  opciones cerradas (o casi), sin contenido libre que el modelo pueda
  colar como respuesta real.

Además, `settings={"variant": None, ...}` es obligatorio en ambas
llamadas, no opcional -- descubierto en ejecución real: `encode_image()`
en esta revisión pinneada del modelo hace `settings["variant"]` sin
`.get()`, así que cualquier `settings` sin esa clave revienta con
`KeyError` antes de generar nada. No es un parámetro elegido, es un
requisito de esta revisión concreta para poder pasar `settings` en
absoluto (controla selección de variante LoRA, no relacionado con
calidad de imagen).

*Consecuencias*: (+) el caption pasó de texto sin sentido ("En una escena
real, los personas... Se manejan y comengan a comer") a descripciones
coherentes y fieles a la foto real ("A group of friends gathers for an
outdoor meal, sharing food and drinks in a casual, relaxed atmosphere");
(+) PERSONAS/AFICION/PAREJA/TEXTO_VISIBLE siguen en español, consistente
con el resto del proyecto; (-) el informe mezcla dos idiomas en un mismo
campo del pipeline (caption en inglés, señales estructuradas en español)
-- documentado explícitamente en vez de ocultado, y limitado a un único
campo visible (`visual_description_general`); (-) dos llamadas al modelo
en vez de una, mitigado reutilizando la misma imagen ya codificada (no se
paga el coste de codificarla dos veces).

=== ADR-22: Redimensionado dedicado al `crop_size` de Moondream2, independiente del usado por DINOv2

*Contexto*: `encode_image()` de Moondream2 no hace una sola pasada por el
encoder de visión -- trocea la imagen en un crop global (reescalado
internamente a un tamaño base fijo) más varios crops locales solapados de
alta resolución (`prepare_crops()`/`select_tiling()` en el código remoto
del modelo), y CADA crop pasa por el encoder. Medido en producción real
(GTX 1650, revisión pinneada del modelo, leyendo `config.py` de esa
revisión vía `inspect.getsource()` en vez de asumir valores de la
documentación pública): `crop_size=378`, `max_crops=12`. Una foto de
612x408 (ya redimensionada al tope de 1024px que usa
`_MAX_QUEUED_IMAGE_DIMENSION` para DINOv2, ver ADR-9) generaba un tiling
de `(2, 4)` -- 8 crops locales + 1 global = *9 pasadas* por el encoder de
visión, y `encode_image()` por sí solo tardaba ~33s (el 78% del tiempo
total de análisis por foto).

*Alternativas consideradas*: bajar `_MAX_QUEUED_IMAGE_DIMENSION` de
geolocation.py de 1024 a un valor menor para las dos rutas a la vez
(descartado: DINOv2 se beneficia de más resolución para el matching de
escenas contra el índice FAISS, ver ADR-9 -- bajar el tope global
degradaría esa geolocalización sin necesidad, solo para resolver un
problema exclusivo de Moondream2); tocar directamente
`modelo.config.vision.crop_size`/`max_crops` tras cargar el modelo, para
forzar menos crops sin redimensionar nada (descartado: exige mutar
config interna de un modelo con `trust_remote_code=True`, sin garantía de
que otros campos dependientes -- tamaño de buffers, máscaras de atención
-- se recalculen de forma consistente; mayor riesgo que beneficio frente
a la alternativa elegida).

*Decisión*: `_CAPTION_MAX_DIMENSION = 378` en `scene_analysis.py`,
aplicado sobre una COPIA de la imagen (`image.copy()` +
`.thumbnail((378, 378))`) justo antes de `encode_image()` -- nunca sobre
la imagen original, que sigue compartida con DINOv2 en el mismo hilo
concurrente (ver ADR-24 para por qué mutar la imagen compartida sería
además una condición de carrera). Con ambas dimensiones por debajo de
`crop_size`, `select_tiling()` devuelve `(1, 1)`: un único crop local +
el global, 2 pasadas en vez de 9.

*Justificación*: el crop global ya reescala internamente a un tamaño
similar para dar "contexto general" de la escena, que es precisamente lo
que este módulo necesita (descripción general, conteo aproximado de
personas, aficiones visibles, indicio de pareja) -- los crops locales
adicionales solo aportan detalle fino (texto pequeño, objetos lejanos),
irrelevante para estas señales de grano grueso.

*Consecuencias*: (+) medido en producción real: `encode_image()` bajó de
~33s a ~12s en la primera prueba (imagen aún con crops múltiples por
redimensionado insuficiente) y a ~12.3s con el redimensionado a 378px ya
aplicado, con encode+dos llamadas bajando de ~52s a ~25s en total,
cruzando el umbral crítico de `_SCENE_ANALYSIS_TIMEOUT_SECONDS=30s` (ver
ADR-17) -- antes de esto, el análisis de contenido probablemente
descartaba SIEMPRE por timeout en este hardware, silenciosamente, sin que
se notara en la interfaz; (+) como beneficio no buscado, el caption
también mejoró en calidad (menos ruido al combinar información de menos
crops); (-) se pierde capacidad de leer detalle muy fino en la foto --
aceptable para las señales de este módulo, pero relevante si en el futuro
se necesitara ese nivel de detalle (p. ej. para el campo TEXTO_VISIBLE,
ver ADR-23, cuyo acierto en texto pequeño podría verse afectado); (-) el
valor 378 es específico de la revisión pinneada del modelo -- si
`_MODEL_REVISION` cambia alguna vez, hay que reconfirmar `crop_size` leyendo
el `config.py` real de la nueva revisión, no asumir que se mantiene.

=== ADR-23: Campo TEXTO_VISIBLE, enlace por foto en publicaciones con varias imágenes, y descripción visual reconstruida solo con señales positivas

*Contexto*: tres necesidades detectadas en uso real de la aplicación, con
soluciones relacionadas entre sí (todas tocan `scene_analysis.py` y/o
`geolocation.py`):

1. Se quería extraer texto legible de la propia foto (carteles,
   escaparates, nombres de lugares) como señal adicional -- motivado por
   un caso real observado antes de este trabajo (un topónimo español
   visible en una foto).
2. Publicaciones de Instagram con varias fotos (`carousel_album`)
   generaban una entrada de `ImageLocationPoint` por foto, pero
   `visual_descriptions`/`general_descriptions` (dos diccionarios en
   `GeolocationOutcome`) usaban el permalink de la PUBLICACIÓN como
   clave -- compartido por todas las fotos del mismo carrusel. Con varias
   fotos de un mismo carrusel analizadas, cada descripción nueva
   SOBREESCRIBÍA a la anterior en el diccionario, así que todas las fotos
   de un carrusel acababan mostrando la descripción de una sola foto (la
   última en procesarse, no determinista por la concurrencia) -- bug real
   confirmado con datos de producción, no solo una hipótesis. Además, el
   enlace mostrado en el frontend para cualquier foto de un carrusel
   apuntaba siempre a la primera (el permalink de Instagram por defecto
   apunta ahí), sin forma de distinguir la foto 1 de la foto 20 de la
   misma publicación.
3. La vista de detalle "qué vio la IA" en el frontend mostraba las cuatro
   líneas estructuradas SIEMPRE, incluidas las negativas por defecto
   (`AFICION: ninguno`, `PAREJA: no`, `TEXTO_VISIBLE: ninguno`) -- ruido
   visual sin valor informativo en la mayoría de fotos, más una cola
   ocasional de texto generado de más por el modelo tras responder bien
   (p. ej. "PERSONAS solo puede val...", cortado por el límite de
   tokens).

*Decisión*: tres cambios relacionados, no independientes entre sí:

- *TEXTO_VISIBLE* como cuarta línea de `_STRUCTURED_QUERY` (ver ADR-21),
  con una salvaguarda EXPLÍCITA propia (no solo la prohibición general del
  final del prompt): nunca puede ser el nombre propio de una persona
  (camiseta, insignia, etiqueta con nombre...), aunque se lea con
  claridad -- en ese caso el modelo debe responder "ninguno" para ese
  campo. Se expone como `InferredAttribute(category="texto_visible",
  confidence=0.4)` -- confianza menor que AFICION (0.5) porque Moondream2
  es un VQA general, no un motor de OCR dedicado. A diferencia de
  AFICION, NO se descarta con varias personas en la foto: un cartel es
  verdad independientemente de quién salga en la imagen, es evidencia
  sobre el lugar/contexto, no un rasgo personal atribuible a una persona
  concreta (ver ADR-18 para el porqué de esa cautela en AFICION).
- *`_photo_link()`* (`geolocation.py`): enlace a una foto CONCRETA,
  usando el parámetro `?img_index=N` de Instagram (1-indexado) cuando la
  publicación tiene más de una foto; con una sola foto, el permalink
  normal sin modificar. Nuevo campo `ImageLocationEstimate.photo_link`
  (al final de la clase, con default `None`, para no desplazar
  construcciones posicionales existentes). `visual_descriptions`/
  `general_descriptions` pasan a indexarse por `photo_link` (único por
  foto) en vez del permalink de publicación (compartido) -- arregla el
  bug de sobrescritura de raíz. `partner_signal_permalinks` se mantiene a
  nivel de PUBLICACIÓN a propósito (una señal de pareja no necesita
  precisión por foto). `ImageLocationPoint.permalink` final usa
  `estimate.photo_link` (con fallback al permalink de publicación).
- *`_build_clean_summary()`* (`scene_analysis.py`): el bloque "qué vio la
  IA" mostrado en el frontend deja de ser el texto crudo del modelo --
  se RECONSTRUYE desde los valores YA PARSEADOS de PERSONAS/AFICION/
  PAREJA/TEXTO_VISIBLE, mostrando solo señales positivas/informativas
  (afición si no es "ninguno", pareja si es "sí", texto visible si lo
  hay; PERSONAS se muestra siempre como contexto básico, no es una señal
  "negativa" en el mismo sentido). Como efecto colateral beneficioso,
  cualquier cola de texto que el modelo genere de más tras responder bien
  queda descartada automáticamente, sin depender de acertar el
  `max_tokens` exacto cada vez.

*Consecuencias*: (+) arregla un bug real de pérdida de datos (descripciones
de carrusel sobrescritas); (+) el enlace de cada foto salta a la foto
correcta dentro de su carrusel (pendiente de verificación 100% fiable por
Nacho -- no se pudo confirmar por búsqueda que Instagram siga soportando
`?img_index=` en la web actual, ver nota en `_photo_link()`); (+) la vista
de detalle deja de acumular líneas vacías, y el artefacto de cola de texto
desaparece sin depender de tuning fino de tokens; (+) como beneficio
colateral, arregla también una colisión de `key` de React en
`LocationMap.tsx` (usaba `point.permalink` como key -- con permalinks
repetidos entre fotos del mismo carrusel, ya era un bug silencioso
independiente); (-) `TEXTO_VISIBLE` añade una nueva categoría de
`InferredAttribute` (`"texto_visible"`) al informe -- sin componente de
frontend dedicado que la muestre aparte (viaja igual que `"aficion"`, sin
UI propia por ahora); (-) el fallback `estimate.photo_link or permalink`
en `report/generator.py` es necesario solo para tests que construyen
`ImageLocationEstimate` directamente sin pasar `photo_link` -- en el flujo
real siempre se rellena.

=== ADR-24: Condición de carrera de PIL entre DINOv2 y Moondream2 sobre la misma imagen

*Contexto*: tras resolver ADR-21/ADR-22 (Moondream2 funcionando de forma
fiable y rápida), apareció un patrón nuevo en producción: analizando
publicaciones reales, exactamente cuando `estimate_location_from_image`
(DINOv2) conseguía una estimación de ubicación para una foto, Moondream2
fallaba para esa MISMA foto con `OSError: image file is truncated (N
bytes not processed)` -- y viceversa, nunca los dos con éxito a la vez.
Confirmado con logging de diagnóstico temporal añadido expresamente para
esto (ver `_collect_photo_result` y la construcción de
`image_location_points` en un momento de este trabajo, ya retirado):
exclusión mutua perfecta entre los dos modelos para la misma imagen.

*Diagnóstico*: `_process_photo` (`geolocation.py`) pasa la MISMA imagen
PIL a `estimate_location_from_image` y `analyze_image_content` EN
PARALELO (`asyncio.gather`, cada una en su propio hilo vía
`asyncio.to_thread`). `_download_image` hacía `Image.open(io.BytesIO(...))`
sin forzar la decodificación -- PIL es PEREZOSO por diseño: no decodifica
los píxeles al abrir, solo guarda una referencia al buffer subyacente y
decodifica bajo demanda la primera vez que algo accede de verdad a la
imagen (`.convert()`, `.copy()`, iterar píxeles...). Esa decodificación
perezosa NO es segura frente a acceso concurrente desde dos hilos
distintos sobre el MISMO objeto: el hilo que llega primero completa la
lectura, el segundo se encuentra el stream ya parcialmente consumido y
recibe justo el error observado.

*Alternativas consideradas*: descargar una copia independiente de la
imagen por cada modelo (dos descargas de red por foto en vez de una --
descartado: duplica tráfico de red y trabajo de decodificación sin
necesidad); serializar los dos análisis (perder la ganancia de
`asyncio.gather`, aunque como se documenta en ADR-25 esa ganancia ya era
mínima en GPU compartida -- descartado igualmente, porque no ataca la
causa real y arrastraría el mismo riesgo si en el futuro alguno de los
dos modelos corriera en un dispositivo distinto donde sí hubiera
paralelismo real que aprovechar).

*Decisión*: forzar la decodificación completa con `image.load()`
inmediatamente después de `Image.open()`, dentro de `_download_image`,
mientras todavía se está en un único hilo (el de la propia descarga) --
antes de que la imagen se reparta entre los dos hilos concurrentes de
`_process_photo`. A partir de ahí, ambos hilos solo LEEN píxeles ya
decodificados en memoria (vía `.convert()`/`.copy()`, que no mutan el
objeto original), lo cual sí es seguro.

*Consecuencias*: (+) ambos modelos consiguen resultado para la misma foto
de forma consistente, confirmado en producción tras el fix ("todas las
fotos analizadas"); (+) cambio de una línea, sin tocar la arquitectura de
concurrencia existente; (-) el bug era preexistente a todo el trabajo de
ADR-21/ADR-22, no introducido por ellos -- simplemente quedaba enmascarado
porque Moondream2 casi nunca completaba un análisis antes (prompts rotos,
timeouts por crops múltiples), así que la exclusión mutua entre los dos
modelos no era observable; al arreglar lo demás, se hizo visible. Sirve
como recordatorio de que arreglar un cuello de botella puede destapar
bugs que ya estaban ahí, no solo mejorar el rendimiento.

=== ADR-25: Concurrencia de fotos consciente de GPU (actualiza ADR-20), paralelismo físico por CUDA streams evaluado y descartado

*Contexto*: `_default_photo_analysis_concurrency()` (ver ADR-20) calcula
`photo_analysis_concurrency` a partir de `os.cpu_count() // 2` --
heurística pensada para cuando Moondream2 corría en CPU (ver ADR-19),
donde varias fotos en vuelo competían por núcleos de CPU. Con GPU, el
recurso limitante deja de ser la CPU: DINOv2 y Moondream2 comparten la
MISMA tarjeta (GTX 1650, 4GB VRAM en la máquina de desarrollo) -- varias
fotos analizándose a la vez ahí no aportan throughput real (la propia GPU
serializa el trabajo de todas formas, ver más abajo) y sí añaden riesgo
real de agotar VRAM.

Aparte, surgió la pregunta de si DINOv2 y Moondream2 podrían llegar a
ejecutarse en paralelo FÍSICO de verdad dentro de una misma foto (no solo
concurrencia a nivel de `asyncio`, que no implica paralelismo de cómputo
real en una GPU compartida vía CUDA: el driver serializa el trabajo de
los dos hilos sobre el mismo dispositivo, así que el tiempo total de
`asyncio.gather` en la práctica es aproximadamente la SUMA de ambos
tiempos, no el máximo -- contra la intuición de que "asíncrono" implica
"en paralelo").

*Alternativas consideradas para paralelismo real*: `torch.cuda.Stream()`
por modelo, para que el planificador de la GPU pueda intercalar trabajo
de verdad entre ambos. Evaluado y DESCARTADO por tres motivos concretos,
no solo por precaución genérica: (a) la VRAM ya está ajustada (picos de
~4.2-4.9GB medidos con Moondream2 en solitario en una tarjeta de 4GB --
paralelismo real aumentaría el riesgo de quedarse sin memoria, justo lo
contrario de lo deseable en producción); (b) una GPU pequeña sin margen
de cómputo ocioso que aprovechar tiene poco que ganar con streams (el
beneficio de esta técnica depende de que haya capacidad sobrante que un
segundo trabajo pueda usar mientras el primero espera, memoria
principalmente); (c) el techo de mejora teórico es pequeño de todas
formas -- DINOv2 es rápido (~1-2s, una sola pasada de embedding) frente a
Moondream2 (~15-25s tras ADR-22), así que aunque se solapara DINOv2 a la
perfección dentro de la ventana de Moondream2, el ahorro máximo posible
son esos 1-2s, no una fracción relevante del total. Gestionar streams a
mano añade además sincronización manual, superficie de error real (se
acaba de arreglar un race condition genuino de PIL en este mismo
pipeline, ver ADR-24) para un beneficio marginal.

*Decisión*: dos cambios, ninguno de ellos implementación de paralelismo
físico real.

1. `_default_photo_analysis_concurrency()` comprueba `torch.cuda.is_available()`
primero (import envuelto en `try/except ImportError`, para no romper
builds sin `WITH_GEOLOCATION` que no tienen `torch` instalado en
absoluto, ver ADR-15): si hay CUDA disponible, devuelve `1`
incondicionalmente, sin mirar `os.cpu_count()`. Sin GPU (o sin `torch`),
se mantiene la heurística de CPU original de ADR-20 sin cambios.
2. Documentar explícitamente (aquí) que no se implementa paralelismo
físico real vía CUDA streams, y por qué -- para que quede como decisión
consciente y razonada en la memoria del TFG, no como una limitación no
explorada.

*Consecuencias*: (+) elimina la contención de GPU entre varias fotos
compitiendo por la misma tarjeta; (+) decisión autocalibrada, igual
criterio que ADR-20 -- no hace falta tocar nada al cambiar de máquina,
sea con GPU o sin ella; (+) la concurrencia 1 en GPU es coherente con la
explicación de por qué `asyncio.gather` no da paralelismo físico en un
único dispositivo -- no tiene sentido reservar más de un hueco de
concurrencia para un recurso que de todas formas se sirve en fila; (-) el
tiempo total por foto en GPU no mejora con esta decisión (nunca lo hizo,
`asyncio.gather` no aportaba paralelismo real ahí) -- lo que mejora es
evitar que MÚLTIPLES fotos compitan a la vez por la misma tarjeta, un
problema distinto; (-) si en el futuro se despliega en una GPU con VRAM y
cómputo sobrados, esta decisión (concurrencia 1 fija) sería
conservadora de más -- documentado como punto a revisitar si cambia el
hardware objetivo, igual que CUDA streams queda como opción válida a
reconsiderar en ese escenario, no descartada para siempre.

=== ADR-26: Backend internacionalizable por códigos estables, no por texto ya renderizado en español

*Contexto*: al añadir selección de idioma (español/inglés) en la webapp
(`react-i18next`, ver `webapp/src/i18n`), quedó fuera del alcance inicial
todo el texto que el backend generaba ya renderizado en español:
1) los nombres de fase del stream de progreso SSE (`"Leyendo
publicaciones..."`, `"Analizando tu forma de escribir..."`, ver
`app/progress.py`); 2) las notas explicativas de cada escalón de
`estimate_population_narrowing` (`PopulationNarrowingStep.note`, ver
`app/scoring/k_anonymity.py`); 3) `attribute_label`, que mezclaba en un
único string una plantilla y un valor (`f"Sexo: {findings.sexo}"`,
`f"Universidad: {findings.universidad.title()}"`); y 4) el veredicto y
las conclusiones que genera Mistral AI (`app/ai_analysis.py`), el único
caso de texto realmente libre de los cuatro.

*Alternativas consideradas*: traducir en el frontend el texto en español
tal y como llega, con una tabla de búsqueda (`{"Leyendo publicaciones...":
"Reading posts..."}`) o parseando con regex los casos con un valor
interpolado (`"Sexo: (.+)"`) -- descartado para (1)-(3): funciona
mientras el backend no cambie ni una coma de redacción, pero se rompe en
silencio (sin error, solo deja de traducir) en cuanto alguien retoque el
texto en español sin saber que el frontend depende literalmente de esa
cadena; y para `attribute_label` en concreto, además, algunos valores son
nombres propios (universidad, empresa, topónimos) que NO deben
traducirse, y una regex no puede distinguir eso de forma fiable. Para (4)
(veredicto/conclusiones de la IA), traducir con una segunda llamada
(a Mistral otra vez, o a un servicio de traducción como DeepL) --
descartado: añade latencia, un segundo punto de fallo, y consume cuota
extra del tier gratuito de Mistral en cada informe, para un texto que ya
sale bien calibrado en español (ver ADR-10) sin ninguna ganancia de
fiabilidad frente a pedirle directamente al modelo que responda en otro
idioma en la misma llamada.

*Decisión*: dos patrones distintos según el tipo de contenido, ambos
aditivos (nunca se elimina el campo en español existente, para no romper
nada que ya dependa de él -- logs, la descarga JSON del informe, un
frontend desplegado con una versión anterior sin estos campos):

1. *Conjuntos cerrados de texto fijo* (fases del SSE, notas de
`k_anonymity.py`, y la plantilla de `attribute_label` separada de su
valor) -- el backend emite un CÓDIGO estable e independiente de idioma
junto al texto en español ya existente, mismo patrón ya usado para
`risk_level`/`source`. Concretamente: `app/stages.py` (7 códigos para
`stage`), `app/note_codes.py` (14 códigos para `note_code`), y en
`PopulationNarrowingStep`/`PopulationEstimate` dos campos nuevos,
`value_raw` (el valor sin la plantilla de `attribute_label` ya montada)
y `location_level` (`"municipio"|"provincia"|"comunidad_autonoma"`,
necesario porque los tres comparten `category="ubicacion"` pero cada uno
usa una plantilla distinta). El frontend traduce con
`t('dashboard.attribute.' + template, { value })`, traduciendo también
`value` solo cuando pertenece a un conjunto cerrado con entrada en el
diccionario (sexo, estado civil, estudios...); nombres propios y números
se interpolan tal cual. Si un campo nuevo no viene (backend antiguo) o la
clave de traducción no existe todavía, se usa el texto en español
existente (`attribute_label`/`note`/el propio código) como fallback, sin
romper -- ver `buildAttributeLabel`/`buildNote` en
`PopulationNarrowingTable.tsx` y el `defaultValue` en `Dashboard.tsx`.

2. *Texto libre generado por IA* (veredicto/conclusiones) -- se genera
DIRECTAMENTE en el idioma pedido, en la misma llamada. El endpoint
`POST /analyze/ai-summary` acepta un query param `lang` (webapp manda su
idioma de UI actual); `analyze_report_with_ai` añade una instrucción de
idioma al prompt de sistema ya calibrado
(`_LANGUAGE_INSTRUCTIONS`) cuando `lang != "es"`. Un valor de `lang` no
soportado (`SUPPORTED_LANGUAGES`) se ignora silenciosamente y se sirve en
español -- es una preferencia, no un contrato.

*Justificación*: los códigos son la solución correcta para conjuntos
cerrados y pequeños porque el frontend ya tenía la infraestructura de
traducción montada (mismo patrón que `risk_level`/`source`) y el coste es
puramente mecánico -- ningún prompt ni cálculo cambia, solo se etiqueta
mejor lo que ya existía. Generar directo en el idioma pedido es la
solución correcta para la IA porque los modelos instruction-tuned
actuales siguen instrucciones de idioma de forma fiable sin necesitar
recalibrar el prompt semántico, y evita el coste/riesgo de una segunda
llamada.

*Consecuencias*: (+) el frontend queda con todo el contenido generado por
el backend traducible, cerrando el hueco que dejó explícitamente
pendiente la introducción de i18n en la webapp; (+) diseño aditivo y con
fallback en cada punto -- un backend desplegado con una versión anterior
(sin `note_code`/`value_raw`/`location_level`, o sin soporte de `lang` en
el endpoint de IA) sigue funcionando, solo sin traducir esas partes
concretas, nunca rompe; (+) tests de backend y frontend en verde sin
modificar ningún test existente salvo por los mocks que usaban
literalmente el texto en español antiguo del stream SSE (que ahora usan
el código correspondiente); (-) cualquier fase, nota o categoría de
atributo NUEVA que se añada en el backend en el futuro necesita también
su entrada correspondiente en `webapp/src/i18n/locales/{es,en}.json`, o
se mostrará en español por el mecanismo de fallback -- no es un error,
pero si se olvida, esa pieza concreta queda sin traducir hasta que
alguien lo note; (-) el prompt de Mistral no está EXPLÍCITAMENTE
calibrado ni evaluado en inglés (ver ADR-10 sobre la calibración en
español), así que la calidad del veredicto/conclusiones en inglés
depende de la capacidad multilingüe general del modelo, no de un ajuste
propio -- validar eso con casos reales queda como trabajo futuro si se
decide dar más peso al público angloparlante.

*Nota de proceso*: esta decisión se implementó y documentó originalmente
como "ADR-21", pero se perdió de este fichero al fusionarse con otra
tanda de cambios (ADR-21 a ADR-25 actuales, sobre Moondream2) preparada
en paralelo en otra sesión, sin que ninguna de las dos partes lo
detectara hasta una revisión posterior del estado del repo. Se
recupera aquí con el número que le corresponde en la secuencia actual
(ADR-26). Motivo documentado en el registro de trabajo (sección 49) como
lección para evitar que se repita: re-clonar el repo antes de tocar
ficheros que otra sesión pueda haber tocado en paralelo, en vez de
asumir que la copia local sigue siendo la última.

=== ADR-27: Estimación indirecta de tramo de edad, con umbral de confianza propio y sin sustituir nunca una edad exacta

*Contexto*: hasta ahora, `edad` solo se rellenaba con una
autodeclaración EXPLÍCITA ("tengo 24 años"), detectada por regex o por
la IA leyendo una frase literal. Si el texto no contenía una frase así,
el escalón de edad de `estimate_population_narrowing` simplemente no
aparecía en el informe, aunque hubiera pistas indirectas razonables
(año de graduación, curso que la persona menciona estar haciendo,
jerga o referencias generacionales) de las que un lector humano sí
podría deducir una franja de edad plausible.

*Alternativas consideradas*: (1) reutilizar sin más el mecanismo de
`inferencias_blandas`/`InferredAttribute` ya existente -- descartado
porque esas inferencias son deliberadamente ajenas al estimador de
k-anonimato (no narrowean población, ver docstring de
`soft_inferences` en `DemographicFindings`), y aquí el objetivo
explícito era justo lo contrario: que la estimación SÍ afecte al
número de población restante que ve el usuario. (2) Pedir a la IA una
edad EXACTA también para el caso indirecto (mismo campo `edad` que ya
existe) -- descartado: mezclaría en un único campo autodeclaraciones
literales (alta fiabilidad) con conjeturas basadas en pistas sueltas
(fiabilidad mucho menor), sin forma de que el informe distinguiera
ambos casos ni de aplicar un umbral de confianza distinto a cada uno.
(3) Devolver directamente un tramo de INE como string libre desde el
prompt (p. ej. que el modelo escriba `"25-29"`) -- descartado frente a
pedir una edad numérica aproximada y convertirla con la función
`age_bin()` ya existente: es más robusto (el modelo puede alucinar un
formato de tramo distinto al de `AGE_DISTRIBUTION_5Y`, p. ej. "25 a 29"
o "26-30") y evita introducir una segunda fuente de verdad para los
límites de los tramos.

*Decisión*: nuevo campo `DemographicFindings.edad_rango` (tramo
quinquenal, mismas claves que `AGE_DISTRIBUTION_5Y`), rellenado
ÚNICAMENTE por `ai_attribute_extraction.py::_set_edad_rango`, nunca por
regex. El prompt de Mistral incorpora un campo aparte,
`"edad_estimada": {"edad_aproximada": <entero>|null, "confianza": <0-1>}`,
con instrucciones explícitas de razonar de forma INDIRECTA/simbólica
(mismo estilo que `estado_civil`, ver ADR previo sobre inferencias
blandas) y de ser conservador con la confianza. Reglas de aceptación,
en este orden:

1. Si ya existe una edad EXACTA (`findings.edad`, autodeclarada por
   regex o por IA) para esa misma persona, `edad_estimada` se ignora
   por completo -- la edad exacta es siempre más precisa y nunca
   conviven ambos campos a la vez.
2. Si `confianza < 0.5`, se descarta también -- no se añade ni edad ni
   tramo. El umbral es deliberadamente más alto que el rango 0.3-0.7
   que se acepta sin filtrar para `inferencias_blandas` genéricas,
   precisamente porque esto SÍ participa en el cálculo de
   k-anonimato (a diferencia de las inferencias blandas).
3. Si supera el umbral, `edad_aproximada` se convierte al tramo INE
   correspondiente con `age_bin()` y se guarda con
   `source["edad_rango"] = "ia_estimada"` (nunca `"ia"` a secas) y su
   confianza en el nuevo campo genérico `DemographicFindings.confidence`
   (dict por campo, pensado para poder reutilizarse en el futuro con
   otros atributos probabilísticos sin volver a cambiar la forma de la
   clase).

`scoring/k_anonymity.py::_step_edad` prioriza `edad` sobre `edad_rango`
(mismo orden que la regla 1 de arriba) y, cuando usa el tramo, aplica
la proporción de `AGE_DISTRIBUTION_5Y` (no la derivada año a año de
`AGE_DISTRIBUTION_1Y`, que no tendría sentido sin conocer la edad
exacta dentro del tramo). La confianza se expone como campo propio
(`PopulationNarrowingStep.confidence` / `PopulationEstimate.confidence`)
en vez de interpolarse dentro de `note` -- ver ADR-26: todas las
`note` de `k_anonymity.py` son deliberadamente texto fijo por
categoría/fuente para que el frontend las traduzca por `note_code` sin
parsear frases, e interpolar un número variable ahí habría roto ese
contrato.

*Justificación*: separar `edad_rango` de `edad` en vez de mezclarlos
mantiene la misma garantía de trazabilidad que ya tiene el resto del
proyecto -- el informe siempre puede distinguir "esto lo dijiste tú
literalmente" de "esto lo ha deducido una IA de pistas sueltas", igual
que ya ocurre con `sexo`/`sexo_por_nombre` (ADR-13) y con
`estado_civil` (inferencia simbólica). Usar el tramo quinquenal ya
publicado por el INE en vez de fingir precisión año a año para un dato
que en realidad es una conjetura es, además, más honesto de cara al
usuario: la incertidumbre de la estimación queda reflejada en la
propia granularidad del dato mostrado, no solo en una nota al pie.

*Consecuencias*: (+) el informe puede mostrar un indicio de edad
incluso cuando el usuario no lo ha declarado explícitamente, sin
necesidad de adivinar un año concreto ni de aceptar estimaciones poco
fundamentadas (el umbral de confianza filtra las conjeturas débiles
antes de que lleguen al cálculo de k-anonimato); (+) coherente con el
patrón ya establecido de "código de fuente + nota" para señalar menor
fiabilidad (`ia_estimada`, icono 🤖 reutilizado en el frontend); (+)
cero cambios de comportamiento cuando ya existe una edad exacta o
cuando no hay `MISTRAL_API_KEY` configurada (degradación con gracia,
mismo principio que el resto de `ai_attribute_extraction.py`); (-) el
umbral de confianza de 0.5 es una elección heurística, no calibrada
contra casos reales etiquetados a mano -- queda como trabajo futuro
si se observa en producción que el modelo es sistemáticamente
demasiado (o poco) conservador con este campo concreto; (-) al ser un
tramo de 5 años en vez de una edad puntual, reduce algo la población
respecto a una edad exacta, pero mucho menos que un año concreto --
efecto esperado y deseado, no un error: es justo la contrapartida de
tener menos certeza sobre el dato de partida.

=== ADR-28: Offload de DINOv2 a una iGPU vía un proceso worker aislado (no en el propio backend)

*Contexto*: ADR-25 fija la concurrencia de fotos a 1 cuando hay CUDA
disponible, precisamente porque DINOv2 y Moondream2 comparten la MISMA
GPU dedicada (GTX 1650, 4GB VRAM en la máquina de desarrollo) -- toda
foto paga la suma de ambos tiempos, no el máximo. En máquinas con,
además de la GPU dedicada, una segunda GPU integrada en el procesador
(iGPU Intel/AMD), surge la posibilidad de mover el modelo más ligero
(DINOv2, ~1-2s por foto) a esa segunda tarjeta vía DirectML y dejar la
dedicada solo para Moondream2 (~15-25s), evitando la contención sin
tocar el análisis de VRAM/streams ya descartado en ADR-25.

Un primer intento instaló `torch-directml` directamente dentro del
entorno del backend. `torch-directml` fija una versión concreta de
`torch` (2.4.1 en el momento de escribir esto) como dependencia --
incompatible con el rango + build CUDA (`cu121`) que el backend ya usa
para Moondream2 (ver requirements-vision.txt). Al instalarlo, `pip`
intentó reinstalar `torch` con esa otra versión/build y la
desinstalación del `torch` anterior falló a medias con un
`OSError: [Errno 5] Input/output error`, dejando el entorno del
backend corrupto y obligando a reconstruir la imagen desde cero.

*Alternativas consideradas*:

1. *Reconciliar versiones*: fijar `requirements-vision.txt` a
`torch==2.4.1` (la versión que exige `torch-directml`) y re-validar
que Moondream2 sigue funcionando con ella. Descartada: la maquinaria
de dtype casting (`_upcast_bfloat16_tensors()`, ver ADR-16/ADR-22) y
`device_map={"": "cuda"}` en dict (necesario para la GTX 1650, sm_75)
está validada contra la versión de `torch` actual, mucho más reciente
-- bajar de versión no es solo cambiar un pin, exige repetir esa
validación entera, con riesgo de romper algo que ya funciona para
ganar algo que hoy es opcional. Además `torch-directml` apenas recibe
actualizaciones, así que reconciliar ataría el backend entero a una
versión de `torch` vieja de forma indefinida.
2. *Proceso worker aislado* (elegida, ver más abajo).

*Decisión*: DINOv2 sobre DirectML corre en `backend/igpu_worker/`, un
proceso Python COMPLETAMENTE aparte -- imagen Docker propia, `venv`
propio, nunca comparte `site-packages` con el backend. Expone dos
endpoints HTTP (FastAPI, ya dependencia del backend, así que
`httpx` para el cliente no añade nada nuevo):

* `GET /devices`: lista los dispositivos DirectML visibles desde el
  worker. El backend (que conoce el nombre de su propia GPU dedicada
  vía `torch.cuda.get_device_name`) es quien decide, comparando
  nombres, si alguno está de verdad libre -- si el único dispositivo
  DirectML visible resulta ser la misma GPU dedicada expuesta con otro
  nombre (pasa con algunos drivers), usarlo no libera nada y se
  descarta.
* `POST /embed`: calcula el embedding DINOv2 (normalizado L2) de una
  imagen en el dispositivo indicado.

El backend decide una sola vez, en `_lazy_load()`
(`_select_igpu_worker_device_index()` en `app/vision/geolocation.py`),
si despachar al worker; `estimate_location_from_image()` intenta el
worker primero y cae al modelo local (mismo comportamiento de siempre,
compartiendo la GPU dedicada) ante cualquier fallo -- worker no
arrancado, timeout, o un operador de DINOv2 sin soporte todavía en
DirectML (cobertura incompleta, ver README de `torch-directml`). El
primer fallo se recuerda (`_igpu_worker_failed`) para no reintentar el
worker en cada foto siguiente, mismo patrón que el fallback CPU
original de DirectML antes de este ADR.

Arrancar el worker es opt-in en dos niveles independientes: el flag
`ENABLE_IGPU_OFFLOAD` (`Settings`, desactivado por defecto) y el
servicio `dinov2-igpu-worker` en `docker-compose.yml`, tras
`profiles: [igpu]` (`docker compose --profile igpu up`) -- nunca
arranca con un `docker compose up` a secas, ni siquiera construye su
imagen, para no imponer la dependencia de `torch-directml` en máquinas
sin iGPU. Tampoco publica su puerto al host (`ports:` ausente a
propósito): solo es alcanzable desde `backend` por la red interna
`monitor-net`, lo que además responde al hotspot de seguridad de
SonarCloud sobre `igpu_worker_url = "http://..."` (sin HTTPS) --
justificado ahí mismo, en el propio comentario de
`Settings.igpu_worker_url`: no hay tramo de red expuesto que TLS
estuviera protegiendo.

El log de rendimiento (`performance_log.py`) registra
`igpu_offload_used` como estado REAL de cada análisis concreto (no si
el flag estaba activado), para que una comparación de rendimiento
offload/sin-offload no quede contaminada por análisis donde el flag
estaba a `true` pero el worker cayó en fallback silencioso.

*Consecuencias*: (+) el backend nunca vuelve a tocar `torch-directml`
ni su pin de versión -- el problema original (reinstalación de `torch`
corrompiendo el entorno) queda estructuralmente descartado, no solo
evitado con más cuidado; (+) opt-in en dos niveles independientes
(flag + perfil de Compose) y con degradación en silencio ante
cualquier fallo -- una máquina sin iGPU, o con el worker parado, se
comporta exactamente igual que antes de este ADR; (+) separa con
claridad, en el propio log de rendimiento, si una mejora observada
viene de verdad del offload o es ruido de otra variable (ver aviso de
ADR-25 sobre no confundir concurrencia con paralelismo real -- el
mismo cuidado aplica aquí); (-) añade un proceso más que gestionar
(arranque, salud, reconstrucción de imagen) y un salto de red (HTTP,
aunque interno) donde antes había una llamada de función directa --
coste de latencia pequeño pero no nulo por foto, asumido a cambio de
liberar la GPU dedicada para Moondream2; (-) el paso de la iGPU al
contenedor vía `/dev/dxg` + `/usr/lib/wsl` (Docker Desktop sobre
WSL2) no está verificado todavía en una máquina real con esa
configuración -- pendiente de confirmar antes de dar la funcionalidad
por completa, no solo por diseñada.

=== ADR-29: Semáforos independientes por modelo, no uno compartido por foto (pipeline real entre fotos)

*Contexto*: tras ADR-28 (offload de DINOv2 a un worker de iGPU), surgió
la pregunta de si DINOv2 y Moondream2 corrían de verdad en pipeline
entre fotos DISTINTAS -- es decir, si DINOv2 podía avanzar a la foto
N+1 en cuanto terminaba la N, sin esperar a que Moondream2 (mucho más
lento, generación autoregresiva) terminase esa misma foto N. La
respuesta, revisando `_process_photo()`, era que no: `analysis_semaphore`
(un único semáforo, tamaño `Settings.photo_analysis_concurrency`)
envolvía la llamada conjunta `asyncio.gather(estimate_location_from_image,
_maybe_analyze_content)` -- el hueco de una foto no se liberaba hasta
que las DOS terminaban para esa foto, así que aunque DINOv2 acabase en
1-2s, la foto siguiente no podía ni empezar a analizarse hasta que
Moondream2 (15-25s) terminase la actual. El offload de ADR-28 solo
podía ayudar al solapamiento DENTRO de una misma foto (el techo de 1-2s
ya calculado en ADR-25) -- nunca a que DINOv2 se adelantase a la foto
siguiente, con o sin worker de iGPU de por medio: esa puerta estaba
cerrada por este diseño, no por el dispositivo donde corriera DINOv2.

*Decisión*: sustituir el semáforo único por DOS semáforos
independientes, `dinov2_semaphore` y `scene_semaphore`, ambos del mismo
tamaño que antes (`actual_concurrency`, sin tocar la heurística/
calibración de `Settings.photo_analysis_concurrency` ni la cuenta de
`threads_per_inference` de `app/main.py` -- el techo de inferencias
simultáneas no cambia: como mucho `actual_concurrency` DINOv2 +
`actual_concurrency` Moondream2 a la vez, igual que antes, solo que
ahora pueden pertenecer a fotos DISTINTAS en vez de forzosamente a la
misma). Dentro de `_process_photo()`, cada modelo entra en su propio
semáforo por separado, y las dos llamadas se siguen esperando juntas
con `asyncio.gather` para ESA foto en concreto (necesario: el resultado
combinado se vuelca junto, ver `_collect_photo_result`) -- pero eso ya
no bloquea a las fotos siguientes, porque el semáforo de DINOv2 se
libera en cuanto DINOv2 termina, sin esperar al de Moondream2.

El arreglo de la condición de carrera de PIL (ADR-24, `image.load()`
forzado en `_download_image` antes de repartir la imagen entre los dos
modelos) sigue siendo válido sin tocarlo: ambos hilos seguían leyendo
únicamente píxeles ya decodificados, este cambio no introduce ninguna
lectura perezosa nueva ni cambia CUÁNDO se decodifica la imagen, solo
CUÁNDO puede empezar el análisis de la foto siguiente.

*Verificación*: test dedicado
(`test_dinov2_of_next_photo_does_not_wait_for_moondream2_of_previous_photo`)
con dos modelos simulados de duración muy distinta (DINOv2 50ms,
Moondream2 300ms) y `photo_analysis_concurrency=1` a propósito (con
concurrencia ≥2 el semáforo único antiguo también habría dejado
arrancar ambas fotos de golpe, sin distinguir el comportamiento viejo
del nuevo) -- comprueba con marcas de tiempo reales que el DINOv2 de la
segunda foto arranca antes de que termine el Moondream2 de la primera.
Confirmado además revirtiendo temporalmente el cambio de producción
mientras se mantenía el test nuevo: el test FALLA contra el diseño
antiguo (best 384.9323s > 384.9320s, la segunda foto no llegaba a
arrancar antes de que la primera terminase del todo) y pasa contra el
nuevo -- no es una aserción que pase por casualidad con cualquier
implementación.

*Consecuencias*: (+) pipeline real entre fotos distintas, no solo
dentro de la misma foto -- el offload de ADR-28 (o cualquier mejora
futura de velocidad de DINOv2) ahora sí puede traducirse en throughput
total, en vez de quedarse acotado al techo de 1-2s por foto de ADR-25;
(+) cambio quirúrgico (una función y su punto de creación de
semáforos), sin tocar la calibración de concurrencia existente ni el
cálculo de hilos por inferencia; (+) test de regresión que falla de
verdad contra el diseño anterior, no solo pasa con el nuevo -- da
confianza de que mide lo que dice medir; (-) el log de rendimiento
(`per_photo_seconds`, ver `app/log/performance_log.py`) sigue
reportando solo el tiempo TOTAL por foto (DINOv2 + Moondream2 juntos
para esa foto concreta), no cuánto de ese tiempo estuvo genuinamente
solapado con fotos vecinas gracias a este cambio -- diagnosticar CUÁNTO
ayuda el pipeline en la práctica (frente a "si ayuda en absoluto", que
sí queda demostrado aquí) requeriría desglose de tiempos por etapa,
pendiente como posible trabajo futuro si hace falta cuantificarlo para
la memoria; (-) no se ha subido la concurrencia de `dinov2_semaphore`
por encima de la de `scene_semaphore` pese a que, con DINOv2
despachado al worker de iGPU (ADR-28), ya no comparte dispositivo con
Moondream2 y en teoría podría soportar más fotos en vuelo a la vez --
decisión deliberadamente conservadora dado que los primeros datos reales
con offload activo (ver registro de trabajo) apuntan a que la iGPU de
prueba podría ser más lenta que la GPU dedicada para este modelo, así
que subir la concurrencia ahí sin confirmarlo antes arriesgaría
degradar el caso ya incierto en vez de mejorarlo.

=== ADR-30: Traducción de las descripciones visuales de Moondream2 al idioma de la UI

*Contexto*: el análisis de contenido visual (`app/vision/scene_analysis.py`,
Moondream2) genera dos textos por foto, cada uno en un idioma FIJO y
distinto, por motivos ya documentados en el propio módulo: el caption
libre (`descripcion_general`) siempre en inglés (Moondream2 apenas
tiene datos de entrenamiento en español; forzarlo producía frases con
gramática rota, palabras inventadas), y el bloque estructurado
(`personas`/`aficion`/`pareja`/`texto_visible`, vocabulario cerrado más
un campo semi-libre) siempre en español, ya calibrado con varios
arreglos de sesgo documentados en el propio módulo. Hasta este ADR,
ambos se mostraban tal cual al frontend sin tener en cuenta el idioma
de la UI (ver ADR-26) -- un usuario con la interfaz en inglés veía el
bloque estructurado en español igualmente, y viceversa con el caption.

Ya se había descartado una vez traducir el caption con Mistral (nota en
`scene_analysis.py`, junto a `_CAPTION_QUERY`): "reintroduciría el
mismo límite de 2 peticiones/minuto del tier gratuito que motivó pasar
a un modelo local en primer lugar... salvo que se batchee a UNA llamada
por informe en vez de por foto -- no implementado aquí". Este ADR
implementa justo esa solución, pendiente desde entonces.

*Alternativas consideradas*:

1. *Volver a generar directamente en el idioma pedido* (mismo patrón
que ADR-26 usa para el veredicto de Mistral: pedirle al modelo que
responda ya en el idioma de destino, en vez de traducir después).
Descartada para Moondream2: a diferencia de Mistral (un LLM grande y
capaz), Moondream2 es un modelo de visión de solo 1.8B parámetros, con
calibración ya frágil y documentada (varios ADR de este mismo fichero
tratan sesgos concretos de este modelo) -- generar en otro idioma
arriesgaría reabrir esos mismos problemas sin poder validarlo aquí
(este entorno no tiene GPU para probar inferencia real del modelo).
2. *Traducir en el backend con Mistral, en UNA llamada por informe* (la
elegida, ver más abajo).

*Decisión*: los prompts a Moondream2 NO se tocan -- siguen generando
exactamente en el mismo idioma fijo de siempre, sin ningún riesgo para
su calibración. La traducción ocurre DESPUÉS, como una capa aparte:

- `personas` (cerrado: "una"/"varias", nunca "ninguna" -- mismo filtro
que ya aplicaba `_build_clean_summary`) e `indicio_pareja` (booleano):
se exponen como CÓDIGOS ESTABLES (`VisualDescriptionCodes`, dataclass
en `scene_analysis.py` y modelo Pydantic homónimo en `schemas.py`,
convertidos el uno al otro en `report/generator.py` porque
`scene_analysis.py` ya importa de `schemas.py` y un import circular no
es una opción) -- mismo patrón "código estable + traducción en
frontend" que ADR-26 ya estableció para vocabulario cerrado, coste
cero, sin llamada al backend.
- `texto_visible` NUNCA se traduce -- es texto literal leído de la foto
(un cartel, una matrícula), traducirlo falsearía la evidencia. Se
muestra tal cual venga, en cualquier idioma de UI.
- `aficion` (semi-libre) y el caption (`descripcion_general`, libre):
se traducen de verdad, bajo demanda, con una función nueva,
`ai_analysis.translate_texts()`, que reutiliza el mismo proveedor
(Mistral) que ya usa el veredicto -- se extrajo un helper HTTP
compartido (`_call_mistral_chat`) para no duplicar el manejo de
errores (sin API key, cuota agotada, key inválida) entre ambas
funciones. Traduce TODA la lista de textos del informe en una sola
llamada (no una por foto), exactamente lo que la nota de
`scene_analysis.py` dejaba pendiente. Si Mistral no devuelve el mismo
número de elementos que se pidieron, se descarta el LOTE ENTERO (no
hay forma fiable de saber qué traducción es de qué foto) -- un
elemento individual raro dentro de un lote correcto sí se sustituye
por el texto original en vez de tirar todo lo demás.

Como el caption siempre nace en inglés y la afición siempre nace en
español, **nunca hace falta traducir los dos a la vez**: según el
idioma de la UI, como mucho uno de los dos necesita una traducción
real. Esto simplifica bastante el diseño frente a "traducir todo
siempre" -- con solo dos idiomas soportados (`es`/`en`, ver ADR-26), la
dirección de traducción queda determinada sin ambigüedad por el idioma
de UI actual.

Endpoint nuevo, `POST /analyze/translate-descriptions`, mismo patrón
exacto que `/analyze/ai-summary` (ADR-26): registrado ANTES de
`/analyze/{platform}` por el mismo motivo de resolución de rutas de
FastAPI, devuelve 503 (no 500) si la traducción no está disponible, y
un `lang` no soportado o igual a "es" es un no-op (sin llamar a
Mistral), no un error.

En el frontend (`LocationMap.tsx`), un `useEffect` que depende de
`points` Y de `i18n.language` decide, según la dirección que toque,
qué lista de textos mandar a `/analyze/translate-descriptions` --
cacheado en estado de React por la duración de la sesión (no hay
persistencia entre pestañas ni entre análisis, coherente con el diseño
RGPD del proyecto: nada se guarda en disco). Si la traducción falla,
se degrada EN SILENCIO al texto original sin traducir (sin estado de
error visible) -- a diferencia de `AiSummaryCard` (donde sin la
llamada no hay nada útil que mostrar), aquí SIEMPRE hay un texto de
respaldo con contenido real, así que un error de red no debería
alarmar al usuario ni bloquear la lectura del resto del informe.

*Consecuencias*: (+) Moondream2 no se toca -- cero riesgo para su
calibración ya frágil y documentada en otros ADR; (+) una sola llamada
a Mistral por informe (no por foto), mismo cuidado de cuota que ya
rige el resto del proyecto con el tier gratuito; (+) vocabulario
cerrado (personas/pareja) traducido gratis en frontend, sin tocar el
backend para eso; (+) texto_visible nunca se traduce, preservando la
evidencia literal de la foto; (+) degradación en silencio ante fallo
de traducción, coherente con el resto de fallbacks ya documentados en
este fichero (DirectML, worker de iGPU, etc.); (-) el desglose de
`personas`/`aficion`/`indicio_pareja`/`texto_visible` en códigos
estructurados duplica, en esencia, la información que ya llevaba
`visual_description` (el texto en español, sin tocar, que sigue
siendo lo que ve Mistral como contexto del informe y lo que se
mostraba antes) -- se mantiene aposta sin unificar los dos caminos,
para no arriesgar romper el contexto que recibe Mistral en el
veredicto por un cambio pensado solo para el frontend; (-) la
traducción de `aficion`/caption solo se dispara al cargar el informe o
cambiar de idioma, no hay forma de forzar un reintento manual desde la
UI si la llamada falla la primera vez -- aceptable dado que sigue
habiendo texto de respaldo útil, pero queda como posible mejora futura
si se observa que hace falta en la práctica.

=== ADR-31: Traducción local con CTranslate2 en vez de Mistral (sustituye ADR-30)

*Contexto*: ADR-30 implementó la traducción de descripciones de fotos
(afición/caption de Moondream2) con Mistral, reutilizando el mismo
proveedor que ya generaba el veredicto del informe. Revisando la
decisión con más calma: un LLM de propósito general para traducir
frases cortas es un uso desproporcionado -- reintroduce justo la
dependencia de red/cuota que el propio proyecto ya había evitado una
vez para Moondream2 (ver la nota junto a `_CAPTION_QUERY` en
`scene_analysis.py`, que explícitamente descartó traducir el caption
con Mistral por el límite de peticiones/minuto del tier gratuito). Con
la máquina de desarrollo además muy justa de RAM libre, tenía sentido
revisar si había una alternativa más ligera en vez de dar la
implementación de ADR-30 por definitiva.

*Alternativas consideradas* (comparadas por relación calidad/RAM/CPU,
que era el criterio que de verdad importaba aquí):

1. *Mantener Mistral* (ADR-30). Descartada por lo de arriba, y porque
un modelo de traducción dedicado consigue calidad equivalente para
frases cortas con una fracción de los recursos (cifra de referencia de
un comparativo externo: un LLM pequeño de ~2B parámetros necesita del
orden de 1,5GB de RAM y varios segundos por frase en CPU, frente a
20-35MB para un modelo de traducción dedicado por par de idioma).
2. *API de traducción en la nube* (Google Translate y similares).
Descartada: aunque mejora la calidad y no consume RAM local, reintroduce
red + clave de API + cuota (esta vez con coste económico real, no solo
un límite gratuito) y, más importante para este proyecto en concreto,
manda texto derivado sobre la persona analizada (aficiones, contenido de
sus fotos) a un tercero más -- va a contracorriente del diseño de
minimización de datos que ya rige el resto de la herramienta (ADR-17,
consentimiento OAuth, cero persistencia en disco).
3. *Argos Translate* (paquete `pip install argostranslate`, envuelve
CTranslate2 + modelos OPUS-MT ya cuantizados). Evaluada en detalle:
mismo motor de inferencia que la opción elegida, pero con dependencias
adicionales (Stanza para segmentación de frases, OpenNMT-py, extras de
interfaz gráfica) que no hacen falta aquí -- las descripciones de
Moondream2 ya son frases sueltas, no hace falta segmentación automática
de texto largo. Descartada por peso extra innecesario dado el límite de
RAM real de la máquina de desarrollo, a favor de ir directos al motor.
4. *CTranslate2 directo, con los modelos MarianMT (Helsinki-NLP/opus-mt-{es-en,en-es})
convertidos a mano* (la elegida, ver más abajo).

*Decisión*: `app/nlp/translation.py` traduce localmente con CTranslate2
(el motor de inferencia, no `transformers`+`torch`) sobre los
checkpoints MarianMT oficiales de Helsinki-NLP, convertidos una sola
vez con `scripts/convert_translation_models.py` (necesita
`transformers`+`torch`, ya presentes si el backend se construyó con
`WITH_GEOLOCATION=true`) y cuantizados a int8. En tiempo de EJECUCIÓN
solo hacen falta `ctranslate2`+`sentencepiece` -- ligeras, sin
`transformers`/`torch` de por medio para esto -- porque los modelos ya
convertidos llevan sus propios ficheros SentencePiece
(`source.spm`/`target.spm`), suficientes para tokenizar/detokenizar sin
la maquinaria completa de un tokenizador de HuggingFace.

Cifra de referencia (benchmark oficial de OpenNMT/CTranslate2, mismo
tamaño de modelo que OPUS-MT): ~2,3GB de RAM en CPU con
`transformers`+`torch` frente a **~516MB con CTranslate2 en int8** --
la razón de fondo por la que no se reutilizó el `transformers` ya
instalado para Moondream2/DINOv2 también para esto, pese a que hubiera
sido la opción de menos dependencias nuevas.

`app/analysis_router.py::translate_descriptions()` (el endpoint HTTP,
`POST /analyze/translate-descriptions`) NO cambia su contrato desde
fuera -- mismo `lang` como query param, mismo cuerpo `{"texts": [...]}`,
misma respuesta `{"translations": [...]}` -- así que el frontend
(`LocationMap.tsx`) no necesitó ningún cambio al hacer este ADR. Sí
cambia por dentro: como la traducción local nunca depende de red ni
cuota, `translate_texts_local()` (a diferencia de la `translate_texts()`
de ADR-30, ahora eliminada) NUNCA lanza -- cualquier fallo (modelos no
convertidos, librerías no instaladas, error de inferencia) degrada a
devolver los textos originales sin traducir, así que el endpoint ya no
necesita un camino de error 503: siempre responde 200 con algo útil.
Al ser CPU-bound (no I/O), se sigue despachando con `asyncio.to_thread`
para no bloquear el event loop, mismo patrón que el resto del pipeline
de visión.

Se eliminó por completo `ai_analysis.translate_texts()` (y sus tests) en
vez de dejarla como alternativa sin usar -- el motivo de la decisión
queda documentado aquí, no hace falta mantener dos implementaciones
funcionando en paralelo. `ai_analysis.py` conserva únicamente
`analyze_report_with_ai()` (el veredicto/conclusiones del informe),
donde sí hace falta un LLM de propósito general -- ahí la traducción
directa (pedirle a Mistral que responda ya en el idioma pedido, ver
`_LANGUAGE_INSTRUCTIONS`) sigue siendo la decisión correcta, sin
cambios respecto a ADR-26.

*Consecuencias*: (+) traducción sin red, sin clave de API, sin cuota,
determinista -- el mismo texto siempre traduce igual; (+) ~4,5x menos
RAM que la alternativa más liviana con `transformers`+`torch`
(~516MB frente a ~2,3GB), crítico dado lo justa que va la máquina de
desarrollo de RAM libre; (+) `ctranslate2`/`sentencepiece` no
introducen ningún conflicto de dependencias con `torch`/`transformers`
ya fijados para Moondream2/DINOv2 (comprobado con `pip check`); (+) el
endpoint HTTP no cambió de contrato -- cero cambios en el frontend; (-)
calidad de traducción probablemente algo por debajo de Mistral para
jerga informal o aficiones muy específicas (un LLM grande generaliza
mejor fuera del vocabulario de entrenamiento que un modelo de
traducción dedicado) -- aceptable dado el volumen de texto real (una
frase corta por foto, no párrafos); (-) requiere un paso de
preparación manual (`scripts/convert_translation_models.py`) antes de
que la traducción funcione de verdad -- sin ejecutarlo, el
comportamiento es idéntico a antes de ADR-30 (textos sin traducir, sin
romper nada, solo sin la funcionalidad); (-) solo cubre es↔en por
diseño (dos modelos direccionales convertidos a mano) -- añadir un
tercer idioma exige convertir dos modelos más por cada nuevo idioma
(ida y vuelta con cada uno de los ya existentes) y tocar la lógica de
`translate_texts_local()` que hoy infiere el origen a partir de que
solo hay dos idiomas posibles (ver su docstring).

=== ADR-32: Bucle de repetición sin fin con beam_size=1 en la traducción local (corrige parte de ADR-31)

*Contexto*: la primera versión de `translate_texts_local()` (ADR-31)
usaba `beam_size=1` (decodificación voraz, sin búsqueda en haz) a
propósito, con el razonamiento de que estas son frases cortas y
descriptivas donde la calidad extra de la búsqueda en haz no se
notaría, priorizando velocidad en CPU. Probado contra el modelo real
(no los fakes de los tests, que no pueden reproducir este
comportamiento), ese razonamiento resultó estar equivocado de una
forma importante: para el par de fotos/frase de prueba
`"a person playing guitar"`, la traducción no dio un resultado peor,
dio un **bucle de repetición sin fin** -- cientos de repeticiones de
"persona" y "que juega a la" hasta el tope de longitud por defecto
(256 tokens), sin lanzar ninguna excepción. No era una pérdida de
calidad marginal, era un fallo de corrección real, silencioso, que la
degradación best-effort del módulo (pensada para fallos con
excepción, no para "traducciones" sintácticamente válidas pero sin
sentido) no llegaba a detectar.

*Decisión*: `translate_batch()` se llama ahora con tres salvaguardas a
la vez, no solo subiendo el tamaño del haz:

- `beam_size=2` -- el valor por defecto de la propia librería
CTranslate2 (no un valor elegido a mano), sigue siendo barato en CPU
para un modelo de este tamaño.
- `repetition_penalty=1.3` y `no_repeat_ngram_size=3` -- penalizan y
bloquean la repetición directamente, como red de seguridad adicional
por si el haz igual se engancha (la búsqueda en haz reduce mucho este
problema pero no lo elimina del todo por sí sola).
- `max_decoding_length` acotado en proporción al texto de entrada (el
triple de su longitud tokenizada, con un suelo de 30) en vez de dejar
el máximo por defecto de la librería (256) -- limita el desastre
aunque las dos salvaguardas anteriores fallasen.

Como cuarta red de seguridad, ya en el post-procesado de
`translate_texts_local()`: si una traducción sale más de 4 veces más
larga que el texto original (más un margen fijo de 20 caracteres para
frases muy cortas), se descarta y se conserva el texto ORIGINAL sin
traducir para esa posición -- mismo criterio defensivo que ya existía
para traducciones vacías (ver ADR-31), extendido a "sospechosamente
larga". Para las frases cortas que traduce este módulo (una afición,
un caption de una foto), una traducción 4x más larga que la entrada es
casi con certeza basura, no una traducción más detallada de verdad.

Se añadió un test de regresión
(`test_absurdly_long_repetitive_output_falls_back_to_original`) que
reproduce el bucle exacto visto en producción con un traductor falso
que siempre devuelve texto repetido, y se confirmó manualmente
revirtiendo la salvaguarda de longitud mientras se mantenía el test:
sin ella, el test FALLA reproduciendo la misma basura ("persona
persona persona...") que se vio en el log real; con ella, pasa. Se
añadió también un segundo test
(`test_calls_translate_batch_with_safeguards_against_repetition_loops`)
que comprueba que las tres salvaguardas de `translate_batch()` se
piden siempre, no solo que produzcan un resultado concreto (verificar
el resultado exacto de una traducción real necesitaría el modelo
real, que no está disponible en el entorno de tests).

*Consecuencias*: (+) el fallo queda cubierto por un test que lo
reproduce de verdad, no solo por la corrección puntual -- una
regresión futura (p. ej., alguien simplifica `translate_batch()` sin
darse cuenta de por qué tiene esos parámetros) se detectaría de
inmediato; (+) cuatro capas de defensa en vez de una, cada una
independiente -- razonable dado que un fallo silencioso (sin
excepción) es peor que uno ruidoso para un módulo pensado para
degradar solo ante errores; (-) el coste en CPU sube ligeramente
respecto a `beam_size=1` (búsqueda en haz de tamaño 2 en vez de
decodificación voraz), aceptado sin más medición formal porque sigue
siendo un modelo pequeño y la alternativa (voraz) demostró ser
directamente incorrecta, no solo más lenta de calidad equivalente;
(-) el umbral "4x la longitud original" de la salvaguarda de longitud
es una elección heurística, no calibrada contra un corpus de
traducciones reales -- si en el futuro aparecen frases donde una
traducción correcta es legítimamente mucho más larga que el original
(p. ej. un modismo que requiere una perífrasis larga), esa traducción
válida se descartaría igual que la basura; no se ha observado ese
caso en la práctica todavía.

=== ADR-33: Progreso por foto emitido dentro de cada etapa, no en el bucle de acumulación de resultados

*Contexto*: dos bugs reales observados en la pantalla de carga, ambos
con la misma causa de fondo. `estimate_locations_for_posts()` lanza
todas las tareas de foto de golpe (`asyncio.create_task`, una por
foto) pero las CONSUME -- y hasta este ADR, también emitía el
progreso -- en un bucle que recorre `photo_units` en su ORDEN
ORIGINAL, esperando cada `photo_tasks[i-1]` uno detrás de otro:

1. *Las dos pistas de progreso ("Geolocalizando fotos..." y
"Analizando fotos...") subían siempre juntas*, aunque por dentro las
dos etapas (DINOv2 y Moondream2) ya corrieran genuinamente
desacopladas desde ADR-29 (semáforos independientes, pipeline real
entre fotos). El motivo: ambas líneas de `emit_progress()` vivían
juntas en el mismo punto del bucle exterior, así que se disparaban
siempre a la vez para la foto `i`, sin importar que DINOv2 llevara
rato libre mientras Moondream2 seguía trabajando en esa misma foto.
2. *El progreso avanzaba a trompicones* (a veces de 1 en 1, a veces de
4 en 4) en vez de una vez por foto terminada. Motivo: si la foto `i-1`
tardaba más que las siguientes, `await photo_tasks[i-1]` bloqueaba el
bucle aunque las tareas `i`, `i+1`, `i+2`... ya hubieran terminado de
verdad -- en cuanto `i-1` por fin se resolvía, el bucle disparaba de
golpe el progreso acumulado de todas las que ya estaban listas y
esperando su turno.

*Decisión*: la emisión de progreso se mueve DE DENTRO del bucle
exterior A DENTRO de `_process_photo()`, concretamente a los cierres
`_run_dinov2()`/`_run_scene()` -- cada uno emite su propio evento de
progreso justo cuando SU etapa termina para SU foto, con un contador
independiente por pista (`progress_state = {"dinov2": 0, "scene": 0}`,
compartido por todas las tareas de foto de ese análisis, incrementado
sin bloqueo explícito: entre leer y escribir el contador no hay ningún
`await` de por medio, así que el modelo cooperativo de asyncio de un
solo hilo garantiza que ninguna otra tarea puede intercalarse a
mitad). El bucle exterior conserva su recorrido en orden original --
sigue haciendo falta para que `results`/`visual_inferences` salgan
deterministas -- pero ya no le corresponde emitir progreso, solo
delegar el volcado a `_collect_photo_result()`.

Caso especial: si la descarga de una foto falla, ninguna de las dos
etapas llega a ejecutarse -- sin este ajuste, esa foto nunca
incrementaría ningún contador y la barra se quedaría clavada por
debajo del 100% en cuanto fallase una sola descarga (el total ya la
cuenta). Se resuelve incrementando y emitiendo ambas pistas de golpe
en el propio camino de fallo de la descarga, ya que ahí no hay trabajo
real que justifique separarlo en el tiempo.

*Verificación*: test dedicado
(`test_progress_tracks_advance_independently_not_in_lockstep`) con el
mismo montaje que el test de pipelining de ADR-29 (DINOv2 rápido,
Moondream2 mucho más lento, concurrencia 1) pero mirando los EVENTOS
DE PROGRESO en vez de los tiempos internos: comprueba que la pista
rápida (geolocalización) termina del todo antes de que la lenta
(análisis de contenido) emita siquiera su primer evento. Confirmado
revirtiendo temporalmente el cambio de producción mientras se
mantenía el test: falla contra el diseño antiguo con las marcas de
tiempo reales invertidas (la pista lenta emitía su primer evento antes
de que la rápida terminase), y pasa contra el nuevo. El test que
comprobaba el orden de progreso con el diseño antiguo
(`test_returns_every_processed_photo_unfiltered_by_confidence`) se
actualizó para comprobar la propiedad que de verdad importa --cada
pista avanza de forma monótona 1, 2, ..., total, sin asumir ningún
orden de intercalado concreto entre las dos-- en vez de una secuencia
exacta de eventos que ya no tiene sentido garantizar (y que sería
justo el bug si se volviera a cumplir).

*Consecuencias*: (+) las dos pistas de la pantalla de carga ahora
reflejan de verdad lo que pasa por dentro desde ADR-29, en vez de
ocultarlo tras una cadencia de reporte artificial; (+) el progreso
avanza uno por foto terminada, sin trompicones, independientemente de
qué foto en concreto esté tardando más en un momento dado; (+) cambio
contenido a `_process_photo()` y al bucle exterior, sin tocar
`_collect_photo_result()` ni la construcción de `results`/
`visual_inferences`, que siguen siendo deterministas en orden
original; (-) el orden relativo en que se intercalan los eventos de
las DOS pistas entre sí ya no es predecible ni se prueba como tal --a
propósito, ver el test actualizado-- lo cual es correcto (refleja la
concurrencia real) pero significa que cualquier futuro consumidor del
stream de progreso no puede asumir nada sobre ese orden, solo sobre la
monotonía dentro de cada pista por separado.

=== ADR-34: Rasgos físicos manuales (ojos/pelo/piel) recalculados en el backend, no duplicando las tablas del INE en el frontend

*Contexto*: hay atributos físicos visibles en cualquier foto de perfil
(color de ojos, de pelo, tono de piel) que la Ley Orgánica de
Protección de Datos desaconseja inferir automáticamente por
categorizar a la persona por características raciales/étnicas (dato
especialmente protegido, art. 9 RGPD), así que ni `vision/scene_analysis.py`
ni `nlp/ai_attribute_extraction.py` los extraen -- pero si el propio
usuario los declara explícitamente sobre su propio perfil, sí pueden
sumarse al estrechamiento de población igual que cualquier otro rasgo
autodeclarado. El estrechamiento de población (k-anonimato, ADR
"Estimación de k-anonimato sin base de datos sintética" -- ver arriba)
y el cálculo del `privacy_score` viven enteramente en el backend
(`scoring/k_anonymity.py`, `scoring/privacy_score.py`, tablas de
`data/ine_reference.py`); el frontend nunca ha conocido esa lógica ni
esas tablas, solo consume proporciones ya calculadas.

*Alternativas descartadas*: duplicar en el frontend (TypeScript) las
tres tablas nuevas (`EYE_COLOR_DISTRIBUTION`, `HAIR_COLOR_DISTRIBUTION`,
`SKIN_TONE_DISTRIBUTION`) y repetir ahí la multiplicación en cadena de
`_apply_proportion`, para poder actualizar el pictograma sin ida y
vuelta al servidor -- descartado: exactamente el tipo de duplicación de
lógica de dominio entre frontend y backend que el proyecto ha evitado
desde el principio (todas las tablas del INE y el cálculo de
k-anonimato son responsabilidad exclusiva del backend); cualquier
ajuste futuro a esas tablas (p. ej. si el INE publicase cifras propias
para estos rasgos, o cambiase el peso de `inferable_data_risk` en el
score) obligaría a mantener dos implementaciones sincronizadas a mano.

*Decisión*: nuevo endpoint `POST /api/analyze/recalculate` (ver
<<section-building-block-view>>) que recibe el `ExposureReport` ya
generado más una lista de `ManualAttribute {category, value}`, y
devuelve el mismo informe con: (1) los rasgos añadidos a
`inferred_attributes` con `confidence=1.0` (autodeclaración directa,
máxima fiabilidad posible); (2) un paso nuevo por rasgo en
`population_narrowing`, encadenado sobre el `remaining_population` ya
alcanzado por el resto de atributos (mismo `_apply_proportion` que usa
el pipeline automático, `source="manual"` para que
`PopulationNarrowingTable.tsx` lo distinga visualmente -- insignia de
color propio en vez del semántico por riesgo); (3)
`inferable_data_risk`/`overall_score` recalculados. El frontend
(`ManualTraitsSelector.tsx` + `Dashboard.tsx::handleApplyTraits`) se
limita a recoger la selección y sustituir su `ExposureReport` en
memoria por la respuesta completa -- no fusiona campos sueltos.

Las tres tablas de proporciones son estimaciones contextuales
documentadas en el propio código, no cifras oficiales del INE (que no
publica una distribución poblacional de estos rasgos) -- a diferencia
del resto de `ine_reference.py`, cuyo criterio de "tabla desactualizada"
(`stale_tables()`, ver ADR sobre concurrencia/GPU y `app/main.py`) no
aplica aquí porque no hay una fuente oficial que pueda quedarse
desactualizada.

*Gotcha de implementación*: `POST /api/analyze/recalculate` debe
registrarse ANTES que `POST /api/analyze/{platform}` en
`analysis_router.py`. FastAPI/Starlette resuelve las rutas por orden de
registro, no por especificidad; si la ruta paramétrica fuera antes,
capturaría el literal `"recalculate"` como valor de `platform` y la de
recalculo nunca se alcanzaría (404 "Plataforma no soportada:
recalculate", sin ningún error en el arranque que lo delate). Cubierto
por `TestRecalculateEndpoint` en `test_analysis_router.py`, que habría
detectado la regresión si el orden se rompiera de nuevo.

*Consecuencias*: (+) cero duplicación de las tablas del INE ni de la
lógica de k-anonimato/scoring fuera del backend; (+) cualquier cambio
futuro a esas tablas o a los pesos del score se aplica en un único
sitio; (+) el rasgo manual queda visualmente distinguible del resto sin
introducir un tipo de dato nuevo (reutiliza `PopulationNarrowingStep`
con un valor más de `source`); (-) cada alta de rasgo manual exige un
viaje de ida y vuelta al servidor con el informe completo en el cuerpo
de la petición (potencialmente grande si hay muchas fotos analizadas),
en vez de una actualización instantánea en el cliente -- aceptable
dado que es una acción puntual del usuario, no algo que ocurra en un
bucle o con alta frecuencia; (-) cualquier ruta estática nueva que se
añada bajo `/analyze/` en el futuro debe recordar declararse antes que
`/analyze/{platform}` por el mismo motivo (ver gotcha arriba).

=== ADR-35: Atributos que nunca se detectarán automáticamente (origen étnico/racial, salud/discapacidad, opinión política)

*Contexto*: el pipeline automático (`vision/scene_analysis.py`,
`nlp/ai_attribute_extraction.py`) ya infiere de forma autónoma varios
atributos a partir de fotos y texto (edad, aficiones, estado
sentimental...) para alimentar el estrechamiento de población y el
`privacy_score`. El RGPD (art. 9) define como "categorías especiales"
un conjunto de datos con riesgo de tratamiento agravado: origen
étnico/racial, salud, opinión política, creencias religiosas,
orientación sexual, datos biométricos/genéticos y afiliación sindical.
ADR-34 ya excluyó la detección automática de rasgos físicos
(ojos/pelo/piel) como proxy racial/étnico, permitiéndolos solo como
autodeclaración manual del propio usuario -- pero esa decisión se
limita a lo VISUAL y no fija un principio general para el resto de
categorías especiales ni para otras vías de detección (texto).

*Decisión*: tres atributos NUNCA se detectarán de forma automática --
ni por visión (fotos) ni por texto (bios, posts, comentarios), ni
siquiera como "detección textual explícita" de menciones -- en ningún
punto futuro del pipeline:

1. *Origen étnico/racial*: categoría especial de máximo riesgo del
   RGPD. Generaliza y refuerza ADR-34: aquel ADR ya impedía inferirlo
   de fotos (permitiendo solo la autodeclaración manual de
   ojos/pelo/piel); este ADR cierra también la vía textual, que
   ADR-34 no llegaba a mencionar explícitamente.
2. *Salud/discapacidad*: también categoría especial (art. 9 RGPD). El
   INE sí publica proporciones de discapacidad a nivel poblacional
   (podrían alimentar una tabla de k-anonimato con el mismo patrón que
   ADR-34), pero es información médica y se descarta incluso como
   autodeclaración manual -- a diferencia de un rasgo físico visible,
   una condición de salud no es equiparable a "lo que ya se ve en la
   foto de perfil".
3. *Opinión política/afiliación*: también categoría especial (art. 9
   RGPD). El INE no la publica (haría falta recurrir al CIS), y más
   allá de la calificación legal, el riesgo de sesgo o desinformación
   de cualquier inferencia sobre postura política se considera
   demasiado alto para justificar la función, incluso como opción
   manual.

*Alternativas descartadas*: replicar para salud y para opinión
política el mismo patrón que ADR-34 usa para ojos/pelo/piel --
selector manual (`ManualTraitsSelector.tsx`) + tabla de proporciones
(INE para discapacidad, CIS para opinión política) + paso nuevo en
`population_narrowing` vía `POST /api/analyze/recalculate`. Descartada
para ambos casos: aunque el patrón técnico ya existe y sería trivial
de replicar, salud y opinión política son cualitativamente distintas
de un rasgo físico visible -- la primera es información médica; la
segunda tiene, además, un problema de fiabilidad/sesgo que no depende
de la fuente de datos.

*Consecuencias*: (+) el límite del pipeline automático (y de
`ManualTraitsSelector.tsx`) queda documentado como decisión
deliberada, no como omisión -- cualquier ampliación futura que toque
alguna de estas tres categorías debe justificarse explícitamente
contra este ADR, no solo añadirse por analogía con ADR-34; (+) reduce
el riesgo legal/ético del proyecto al no tocar las categorías de mayor
riesgo del RGPD bajo ninguna vía (ni automática ni manual, salvo la
excepción ya acotada de ADR-34 para rasgos físicos); (-) dos fuentes
de datos potencialmente disponibles (discapacidad en INE, opinión
política en CIS) quedan sin aprovechar en el cálculo de k-anonimato,
que en teoría podría ser más completo con ellas.

=== ADR-36: AGE_DISTRIBUTION_1Y pasa a datos reales del Censo (tabla 01003), en vez de repartir uniformemente AGE_DISTRIBUTION_5Y

*Contexto*: `AGE_DISTRIBUTION_1Y` (proporción de población por edad
exacta, año a año) se derivaba de `AGE_DISTRIBUTION_5Y` repartiendo
uniformemente la proporción de cada tramo quinquenal entre las edades
que lo componen -- una aproximación explícitamente documentada como tal
desde el principio, justificada porque la tabla año-a-año real del INE
(https://www.ine.es/jaxi/Tabla.htm?path=/t20/e245/p08/l0/&file=01003.px)
es un selector interactivo, no un CSV descargable directamente por URL.

Al construir `SPORT_PRACTICE_BY_AGE_BAND` (ver ADR-37) cruzando esta
distribución con los tramos de edad de la Encuesta de Hábitos
Deportivos (15-24, 25-54, 55+), el tramo 15-24 -- el más pequeño y por
tanto el más sensible a errores de reparto -- dio una tasa de práctica
deportiva del 100,85% sobre la población derivada: más practicantes
que población, matemáticamente imposible. Señal inequívoca de que el
reparto uniforme dentro de tramo no se ajustaba lo bastante bien a la
pirámide real en esa franja concreta (las edades no se distribuyen
uniformemente ni siquiera dentro de un quinquenio, y el efecto se nota
más cuanto más pequeño es el tramo en términos absolutos).

*Decisión*: descargar manualmente la tabla 01003 (población por edad,
año a año, ambos sexos, año 2022 -- la exportación a CSV desde el
navegador sí es posible aunque la URL directa no lo sea) y usarla como
fuente PRIMARIA de `AGE_DISTRIBUTION_1Y`, invirtiendo la relación entre
las dos tablas: antes `AGE_DISTRIBUTION_5Y` era la fuente y `1Y` se
derivaba de ella; ahora `AGE_DISTRIBUTION_1Y` es la fuente (datos
reales, 101 valores exactos que suman 1.0) y `AGE_DISTRIBUTION_5Y` se
deriva SUMANDO `1Y` dentro de cada tramo quinquenal
(`_build_age_distribution_5y_from_1y`), garantizando que ambas tablas
sean consistentes entre sí por construcción.

*Desfase de año aceptado*: la tabla 01003 es de 2022, mientras que
`TOTAL_POPULATION_ES` es de 2025 (~1,65M más de población total). Se
usa la distribución de 2022 como PROPORCIÓN (no como cifra absoluta)
aplicada sobre `TOTAL_POPULATION_ES` actual, asumiendo que la FORMA de
la pirámide de edad no cambia mucho en 2-3 años aunque el total crezca
-- mismo tipo de aproximación que ya aceptaba la versión anterior
(reparto uniforme dentro de tramo), pero basada en datos reales de
población en vez de un reparto artificial.

*Gotcha de implementación*: un primer intento de generar el diccionario
de 101 valores se transcribió A MANO a partir de una salida de consola
truncada, y 88 de los 101 valores no coincidían con el CSV real (el
error no rompía la sintaxis ni los tests existentes, solo daba
resultados sutilmente incorrectos -- se detectó porque la suma no daba
1.0 exacto). Se corrigió regenerando el bloque completo por script
directamente desde el CSV y sustituyéndolo con una operación de texto
programática, no manual, eliminando el riesgo de transcripción por
completo.

*Consecuencias*: (+) elimina el problema de tasas por encima del 100%
en cualquier cálculo que cruce edad con otra variable, no solo
deportes; (+) mejora la precisión de CUALQUIER cálculo por edad en la
app (k-anonimato de cualquier atributo que use `age_range_proportion`),
no solo el que motivó el cambio; (+) las dos tablas (`1Y` y `5Y`) ya no
pueden desincronizarse entre sí, al derivarse la segunda de la primera
por construcción; (-) el desfase de 2-3 años entre la forma de la
pirámide (2022) y el total poblacional (2025) sigue siendo una
aproximación, aunque mejor que la anterior; (-) requiere descarga
manual periódica si se quiere refrescar (marcado con umbral de
caducidad anual en `_STALE_THRESHOLDS`, ver `stale_tables()`).

=== ADR-37: Práctica deportiva condicionada por sexo, edad y nivel de estudios, con prioridad en cascada (nunca combinando dos ajustes a la vez)

*Contexto*: `SPORT_PRACTICE_DISTRIBUTION` empezó como una tabla de 9
modalidades con cifras sueltas de prensa sobre la edición 2022 de la
Encuesta de Hábitos Deportivos, y se amplió en varias fases hasta las
41 modalidades completas de la tabla 1.21 de la edición 2024/25
(descargada directamente del portal de estadísticas del Ministerio,
tras confirmar que la prensa nunca cita el desglose completo). Todas
esas proporciones son MARGINALES: aplican la misma cifra a cualquiera
que declare esa modalidad, sin distinguir si es hombre o mujer, joven o
mayor, con estudios superiores o sin ellos -- desperdiciando la señal
de otros atributos que la propia persona ya haya declarado.

La tabla 1.22 de la misma encuesta ("...por modalidad deportiva, sexo,
edad y nivel de estudios") sí desglosa cada modalidad por esas tres
variables -- pero como TRES CRUCES INDEPENDIENTES (deporte×sexo,
deporte×edad, deporte×estudios), no como un cruce a cuatro bandas
simultáneo (deporte×sexo×edad×estudios a la vez). Ese dato conjunto no
existe en ninguna tabla publicada de la encuesta.

*Decisión*: construir tres tablas nuevas --
`SPORT_PRACTICE_BY_SEX`, `SPORT_PRACTICE_BY_AGE_BAND` y
`SPORT_PRACTICE_BY_EDUCATION_LEVEL` -- cada una P(deporte | variable),
convertidas de "% de practicantes de ese grupo" a "% de la POBLACIÓN de
ese grupo" multiplicando por la tasa de práctica deportiva específica
de cada grupo (mismo patrón que ya usaba ADR sobre
`MARITAL_STATUS_BY_SEX`, extendido aquí a tres variables en vez de una).
`_step_practica_deportiva` prueba las tres en CASCADA, con prioridad
sexo > edad > nivel_estudios > marginal: usa la primera que esté
disponible Y tenga dato para esa combinación concreta, y si ninguna
sirve, cae a la marginal. NUNCA combina dos ajustes a la vez (p. ej.
sexo Y edad multiplicados) porque, al no existir el cruce a cuatro
bandas, hacerlo equivaldría a asumir independencia estadística entre
sexo y edad DENTRO de cada deporte -- una suposición no verificable con
los datos disponibles, y que probablemente sobre-estimaría el
estrechamiento de población.

El orden de prioridad (sexo > edad > estudios) es por limpieza de la
señal, no por "mejor" en abstracto: sexo es una condición binaria sin
ambigüedad; edad puede tener tramos sin ambigüedad (edad exacta) o con
ambigüedad resoluble (un rango declarado que cabe entero dentro de un
tramo de la encuesta -- ver `_sport_age_band`, que devuelve `None` si
el rango cruza la frontera entre dos tramos, en vez de adivinar);
nivel de estudios depende ADEMÁS de una aproximación de población
adicional (`EDUCATION_LEVEL_DISTRIBUTION`, basada en población de 25 a
64 años, ver ADR-38) que ni sexo ni edad necesitan, así que va último.

*Casos de muestra insuficiente*: cuando la encuesta redondea el % de
una combinación concreta a 0,0 (p. ej. "squash" y mujeres, o
"automovilismo"/"triatlón" en el tramo 55+), esa clave se OMITE a
propósito de la tabla condicionada en vez de guardarse como 0.0 literal
-- un 0,0% redondeado significa "muestra insuficiente para detectarlo",
no "cero personas lo practican". Al faltar la clave,
`_step_practica_deportiva` cae de vuelta al siguiente nivel de
prioridad (o a la marginal), en vez de mostrar una población de 0 que
la evidencia real no respalda.

*Efecto colateral positivo, no buscado*: construir
`SPORT_PRACTICE_BY_AGE_BAND` fue precisamente lo que expuso el problema
de tasas por encima del 100% que llevó a ADR-36 (sustituir
`AGE_DISTRIBUTION_1Y` por datos reales del Censo) -- un ejemplo de cómo
cruzar una tabla nueva contra infraestructura ya existente puede sacar
a la luz aproximaciones que llevaban tiempo sin cuestionarse.

*Consecuencias*: (+) aprovecha la señal de sexo/edad/estudios cuando ya
se conoce, en vez de desperdiciarla aplicando siempre la marginal; (+)
el efecto es grande para deportes con sesgo fuerte por cualquiera de
las tres variables (p. ej. "caza" lo practican los hombres ~32 veces
más que las mujeres, "yoga_pilates" las mujeres ~4 veces más que los
hombres); (+) cada tabla condicionada documenta explícitamente sus
casos de muestra insuficiente, en vez de esconderlos como ceros; (-) la
cascada de prioridad es una simplificación deliberada frente al cruce a
cuatro bandas real, que no existe como dato público; (-) tres tablas
más que mantener y actualizar cuando la encuesta publique su siguiente
edición.

=== ADR-38: Nuevo atributo `nivel_estudios` (nivel de formación alcanzado), distinto de `estudios` (carrera concreta)

*Contexto*: al construir `SPORT_PRACTICE_BY_EDUCATION_LEVEL` (ver
ADR-37) para aprovechar la columna de nivel de estudios de la tabla
1.22, se encontró que el proyecto no tenía NINGÚN atributo que
capturase el nivel de formación alcanzado en los tramos que usa la
propia encuesta (1ª etapa de secundaria o inferior / 2ª etapa de
secundaria / educación superior). El campo `estudios` ya existente
(`STUDIES_DISTRIBUTION`) es una cosa distinta: la CARRERA universitaria
concreta que alguien nombra ("estudié Medicina"), que solo aplica a
quien ya cursa o cursó estudios superiores CON una titulación nombrada
-- no cubre a quien solo dice "tengo el bachillerato" o "no tengo
estudios", y no permite construir la tabla condicionada sin ese dato.

*Decisión*: añadir `nivel_estudios` como atributo nuevo de punta a
punta (regex + extracción por IA + paso de k-anonimato propio,
`_step_nivel_estudios`), con 3 valores: `superior`,
`secundaria_superior`, `secundaria_o_inferior` -- clasificación
CNED-2014/ISCED que usa el INE/EPA. Requiere una autodeclaración de
haber COMPLETADO ese nivel (verbos como "tengo...", "terminé...", "soy
licenciado/a en..."), no de estar cursándolo actualmente ("estoy
estudiando en la universidad" no cuenta) -- mismo criterio que
`practica_deportiva` exige práctica real, no mención de espectador.

Los Ciclos Formativos de Formación Profesional son el caso más
delicado: un Ciclo Formativo de Grado SUPERIOR cuenta como "superior"
en la clasificación del INE (nivel 5, igual que la universidad), no
como "secundaria_superior" -- solo el Grado MEDIO cae en ese segundo
tramo. Por eso las frases-ancla exigen "superior"/"medio" explícito en
vez de un genérico "tengo un ciclo formativo" sin cualificar, que sería
ambiguo entre los dos niveles.

Si `estudios` ya está detectado (una carrera universitaria concreta),
`nivel_estudios` se infiere automáticamente como `superior` sin
necesitar una frase-ancla propia -- nombrar la carrera ya es evidencia
suficiente del nivel. Los dos campos pueden coexistir como pasos
separados de `population_narrowing` (no es doble contabilización: son
dos preguntas distintas de la encuesta, "¿qué estudiaste?" frente a
"¿hasta qué nivel llegaste?").

*Limitación de la tabla poblacional, documentada a propósito*:
`EDUCATION_LEVEL_DISTRIBUTION` (el marginal usado cuando no hay sexo ni
edad disponibles para el ajuste condicionado, ver ADR-37) sale del
indicador INE/EPA "Nivel de formación de la población adulta", que
cubre población de 25 a 64 años -- NO toda la población de 15+ que es
la referencia habitual del resto de `ine_reference.py`. Es el rango de
edad estándar que usan INE/Eurostat precisamente porque medir nivel
COMPLETADO en gente más joven (aún cursando) o mayor (con un contexto
de acceso a la educación muy distinto) sesga la comparación en ambos
sentidos -- se documenta la limitación en vez de esconderla, mismo
criterio que otras aproximaciones de este fichero (golf/2022 en una
versión anterior de `SPORT_PRACTICE_DISTRIBUTION`, EYE_COLOR/HAIR_COLOR
en ADR-34).

*Consecuencias*: (+) desbloquea `SPORT_PRACTICE_BY_EDUCATION_LEVEL`
como tercer nivel de la cascada de ADR-37; (+) es reutilizable por
cualquier otro atributo futuro que quiera condicionarse por nivel
educativo, no solo deportes; (-) la aproximación 25-64 sobre población
15+ probablemente sobre-estima "superior" en el extremo joven (mucha
gente de 15-24 aún no ha terminado) y lo infra-estima en el extremo
mayor (65+, generación con menor acceso histórico a estudios
superiores); (-) atributo nuevo completo (regex + IA + paso propio) es
más superficie de mantenimiento que reutilizar algo existente, pero no
había nada reutilizable que cubriera esta pregunta concreta.

=== ADR-39: ngrok + Basic Auth en vez de dominio propio + Cloudflare, para exponer la app fuera de local

*Contexto*: hace falta HTTPS público para poder probar el login de
Instagram (exige `redirect_uri` con HTTPS incluso en desarrollo, ver
README) y para poder enseñar la app fuera de la propia máquina. Ya
existía la nota en el README que descarta `cloudflared tunnel --url`
(Cloudflare Quick Tunnel) por un motivo técnico concreto: su edge
bufferiza por completo las respuestas `text/event-stream`, así que el
streaming SSE de `/api/analyze/{platform}/stream` deja de verse en
tiempo real. Esa nota ya dejaba claro que un *named tunnel* de
Cloudflare (con dominio propio) sí respetaría el streaming -- pero
igualmente no se ha montado, por un motivo distinto y más de fondo.

*Motivo real de no montar dominio propio + Cloudflare*: la app corre
con capacidad de cómputo para **una persona a la vez** (Moondream2 y
DINOv2 comparten los recursos disponibles, ver ADR-29 sobre los
semáforos por modelo). Un dominio propio con Cloudflare por delante
tiene sentido cuando el objetivo es que cualquiera pueda entrar sin
pedir permiso -- exactamente lo contrario de lo que hace falta aquí.
Montar dominio + tunnel con nombre + WAF para luego tener que limitar
igualmente quién entra sería resolver un problema (tráfico público sin
control) que este proyecto no tiene, a costa de más piezas que
mantener (DNS, certificados renovándose, reglas de WAF) para un caso
de uso que es, en la práctica, "que yo pueda entrar desde fuera, y
enseñárselo a alguien puntualmente cuando yo decida".

*Alternativas descartadas*:

- *Dominio propio + Cloudflare Tunnel (named tunnel) + Access*:
  técnicamente resolvería el streaming Y permitiría restringir acceso
  (Cloudflare Access, gratis hasta 50 usuarios). Descartado por lo de
  arriba: es infraestructura pensada para servir a más de una persona
  a la vez, que es precisamente lo que este proyecto no puede hacer
  todavía. Además, el plan gratuito de Cloudflare (a diferencia de
  ngrok) no dio buenos resultados en pruebas propias con las
  actualizaciones de página en tiempo real que necesita el streaming
  SSE de este proyecto -- sin llegar a diagnosticarse con el mismo
  detalle que el problema, ya documentado, de Quick Tunnel.
- *Dominio gratuito (DigitalPlat FreeDomain u otro) sin Cloudflare
  delante*: no resuelve el streaming (seguiría sirviendo directamente,
  sin problema de buffering) pero tampoco aporta nada que ngrok no dé
  ya (dominio estable, HTTPS) -- añadiría un proveedor más sin
  necesidad real.
- *Dominio de pago*: mismo razonamiento que el punto anterior más un
  coste recurrente injustificado mientras el cuello de botella siga
  siendo el cómputo, no el nombre de dominio.

*Decisión*: usar **ngrok** (plan gratuito) con **Basic Auth vía Traffic
Policy** (`backend/policy.yaml`, ver README) como control de acceso. El
plan gratuito de ngrok ya incluye un dominio propio estable (no cambia
entre reinicios) y streaming SSE en tiempo real sin el problema de
Cloudflare, y Traffic Policy permite Basic Auth sin necesidad de plan
de pago -- cubre exactamente las dos necesidades reales (HTTPS estable
+ que solo entre quien yo decida) sin montar infraestructura pensada
para más carga de la que la app puede atender.

*Consecuencias*: (+) cero coste recurrente y cero infraestructura
nueva que mantener (DNS, certificados, reglas de firewall); (+) el
control de acceso vive en un único archivo (`policy.yaml`, fuera del
repo) en vez de repartirse entre proveedor de DNS + Cloudflare Access;
(+) streaming SSE funciona correctamente, a diferencia de Quick
Tunnel; (-) el plan gratuito de ngrok muestra una página intermedia de
aviso la primera vez que alguien abre la URL en el navegador (ver nota
en el README) -- fricción menor, no un problema de seguridad; (-) si
en el futuro la capacidad de cómputo deja de ser el factor limitante
(por ejemplo, si se separa el análisis en una cola con varios
workers), esta decisión habría que revisarla -- en ese momento sí
tendría sentido un dominio propio pensado para más de un usuario
simultáneo.

=== ADR-40: Nuevo atributo `rama_estudios` (rama de conocimiento), sin paso propio cuando `estudios` ya la cubre

*Contexto*: `estudios` (`STUDIES_DISTRIBUTION`) solo cubre 14 carreras
concretas con proporción propia -- cualquier otra carrera mencionada en
el texto ("estudio Sociología", "estudio Filosofía") no aporta ninguna
señal de estrechamiento, aunque sí sea perfectamente clasificable en
una de las 5 ramas de conocimiento oficiales del sistema universitario
español (Real Decreto 1393/2007, modificado por RD 43/2015: Artes y
Humanidades, Ciencias, Ciencias de la Salud, Ciencias Sociales y
Jurídicas, Ingeniería y Arquitectura).

*Decisión*: añadir `rama_estudios` como atributo nuevo de punta a
punta (regex + IA + paso de k-anonimato propio), con dos fuentes de
detección:
  - **Inferencia automática** desde `estudios` cuando ya se conoce una
    de las 14 carreras concretas, vía `STUDIES_TO_RAMA` (mapeo fijo
    1:1, sin ambigüedad -- cada carrera pertenece a exactamente una
    rama oficial).
  - **Vocabulario ampliado propio** (~25 carreras adicionales:
    sociología, filología, física, fisioterapia, ingeniería civil...)
    con su propia frase-ancla de detección, para cubrir carreras que
    `estudios` no tiene registradas individualmente pero sí son
    clasificables en una rama.

Dos casos de la clasificación oficial se verificaron explícitamente por
no ser evidentes en vez de asumirse: "psicología" está adscrita a
Ciencias de la Salud como rama PRINCIPAL (BOE-A-2022-12576, código
RUCT), no a Ciencias Sociales y Jurídicas como podría parecer por su
objeto de estudio; "veterinaria" está adscrita a Ciencias de la Salud
(documentación oficial de admisión de la Universidad de Zaragoza y
catálogo de la USC), no a Ciencias como sugeriría la intuición.

*Guard de no-duplicación (la decisión central de este ADR)*: a
diferencia de `nivel_estudios` (que SÍ genera su propio paso aunque se
infiera automáticamente de `estudios`, porque nivel y carrera son
preguntas distintas de la encuesta de origen -- ver ADR-38),
`rama_estudios` NUNCA genera un paso de estrechamiento cuando
`findings.estudios` ya está informado. El motivo es puramente
estadístico: quien estudia "derecho" ya está, con probabilidad
exactamente 1, dentro de "Ciencias Sociales y Jurídicas" -- no es un
hecho INDEPENDIENTE del ya conocido, es un subconjunto exacto de él.
`_step_estudios` ya aplica la proporción de esa carrera concreta
(3,08% para derecho), que es más precisa que la de toda su rama
(46,66%); aplicar AMBAS multiplicándolas contaría el mismo hecho dos
veces y estrecharía la población sin ninguna base -- el mismo tipo de
error que motivó la cascada de prioridad de ADR-37 (nunca combinar dos
ajustes condicionados que no son independientes entre sí).
`_step_rama_estudios` solo produce un paso cuando `rama_estudios` se
detectó de forma INDEPENDIENTE de `estudios` (carrera fuera de las 14,
vía el vocabulario ampliado). El campo se sigue rellenando igualmente
para mostrarlo de forma informativa en el resto del pipeline, solo se
omite el paso de `population_narrowing`.

*Bug encontrado y corregido de paso, no buscado*: al escribir el test
de regresión numérica para el guard de arriba
(`test_does_not_double_narrow_the_final_remaining_population`, que
compara `final_remaining_population()` con y sin `rama_estudios` cuando
`estudios` ya está presente, esperando que sea idéntico), se descubrió
que `nivel_estudios` (ADR-38) llevaba desde su introducción sin estar
incluido en `_CHAINED_CATEGORIES` -- el conjunto que
`final_remaining_population()` consulta para decidir qué pasos cuentan
hacia el número combinado final. El paso individual de `nivel_estudios`
se calculaba y mostraba correctamente en la lista de
`population_narrowing`, pero si era el ÚLTIMO paso encadenable con
narrowing válido, el número final ("en España hay X personas que
comparten tus rasgos") lo ignoraba y usaba el del paso anterior en su
lugar. Ningún test existente lo cubría porque `TestFinalRemainingPopulation`
no tenía ningún caso con `nivel_estudios` como único o último atributo
encadenable. Corregido añadiendo tanto `nivel_estudios` como
`rama_estudios` a `_CHAINED_CATEGORIES` en el mismo cambio.

*Fuente de la tabla, limitación documentada*: `RAMA_ESTUDIOS_DISTRIBUTION`
mezcla matriculados de universidades PÚBLICAS del curso 2015/16 con
PRIVADAS del curso 2019/20 (Ministerio de Universidades, Estadística de
Estudiantes Universitarios) porque no se encontró una única fuente con
el desglose completo de las 5 ramas para ambos tipos de universidad en
el mismo curso académico. Se validó cruzando con una cifra independiente
de nuevo ingreso del curso 2021/22 (Ciencias Sociales y Jurídicas 46,4%,
Ciencias 6,3% según esa fuente, frente al 46,66%/6,02% calculados aquí)
-- la coincidencia razonable entre ambas cifras, pese al desfase de
cursos y al ser métricas distintas (matriculación total frente a nuevo
ingreso), da confianza en el orden de magnitud sin pretender exactitud
absoluta.

*Consecuencias*: (+) aprovecha menciones de carrera que antes no
aportaban ninguna señal de estrechamiento (cualquier carrera fuera de
las 14 de `STUDIES_DISTRIBUTION`); (+) el guard de no-duplicación es
generalizable como patrón para futuros atributos que refinen uno ya
existente (cualquier "categoría amplia de X" derivada de un "X
concreto" ya cableado debería aplicar el mismo criterio); (+) efecto
colateral positivo: destapó y corrigió un bug real de ADR-38 que
llevaba una sesión entera sin detectarse; (-) la tabla de origen mezcla
dos cursos académicos distintos, aproximación explícitamente
documentada en vez de escondida; (-) atributo nuevo completo (regex +
IA + paso propio) es más superficie de mantenimiento, aunque menor que
`nivel_estudios` al reutilizar `_STUDY_VERB_RE` en vez de un regex de
detección nuevo.
