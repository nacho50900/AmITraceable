[[section-design-decisions]]
== Decisiones de arquitectura

Se documentan como ADR abreviados (contexto / decisión / consecuencias).
Las decisiones de mayor calado ya se resumieron en
<<section-solution-strategy>>; aquí se detallan con sus alternativas
consideradas.

=== ADR-1: Reducir el alcance a un MVP multiplataforma simple

*Contexto*: la propuesta original incluía correlación de identidades
entre Instagram, Twitter/X y Reddit mediante embeddings y clustering.

*Decisión*: MVP centrado en análisis por plataforma individual (Reddit,
luego Instagram), sin correlación cruzada.

*Consecuencias*: (+) alcance viable para un TFG; (+) evita la tensión
ética de comparar contra cuentas de terceros sin consentimiento;
(-) el módulo de correlación entre plataformas queda como trabajo
futuro, sin implementar.

=== ADR-2: Backend en Python (FastAPI) sobre el servicio Node heredado

*Contexto*: la plantilla universitaria (`yovi_en1b`) traía un servicio
`users` en Node/Express.

*Alternativas consideradas*: mantener Node y llamar a un
microservicio Python aparte solo para NLP; reescribir todo en Node
usando bindings de NLP menos maduros.

*Decisión*: sustituir el contenido de `users/` por Python/FastAPI
completo, conservando inicialmente la carpeta y la infraestructura
circundante; renombrada más adelante a `backend/` (ver ADR-7).

*Consecuencias*: (+) acceso directo al ecosistema NLP de Python
(spaCy, scikit-learn) sin llamadas entre servicios; (-) hubo que
reescribir el Dockerfile, los tests y adaptar el instrumentador de
métricas a un paquete distinto (`prometheus-fastapi-instrumentator`
frente a `express-prom-bundle`).

=== ADR-3: Sin persistencia (procesamiento 100% en memoria)

*Contexto*: cumplimiento RGPD y minimización de datos.

*Decisión*: ninguna base de datos; el único estado entre peticiones es
una cookie de sesión firmada con el `access_token`.

*Consecuencias*: (+) cerrar sesión elimina cualquier rastro del
usuario en el sistema; (+) simplifica drásticamente el argumentario
RGPD de la memoria; (-) no hay histórico de análisis previos ni
posibilidad de comparar la evolución del score en el tiempo (aceptado
como limitación conocida).

=== ADR-4: Modelo de datos genérico tras detectar acoplamiento a Reddit

*Contexto*: la primera integración de Instagram normalizaba su media
directamente al modelo `RedditPost`, reutilizando el campo `subreddit`
para el hashtag y forzando una arquitectura "Reddit como plataforma
principal, Instagram adaptándose a su modelo".

*Decisión*: refactor a `SocialPost`/`SocialProfile` con campos neutros
(`group`, `score`, `platform`), y unificación de la ruta de análisis a
`/api/analyze/{platform}` con un diccionario de factories.

*Consecuencias*: (+) añadir una plataforma nueva no requiere adaptar
modelos ajenos; (+) cobertura de tests más simétrica entre plataformas
(pasó de 84% a 93% al parejar los tests de Reddit con los ya existentes
de Instagram); (-) coste de refactor no trivial una vez el código ya
estaba en producción de pruebas.

=== ADR-5: Rechazo de verificación de integridad del lado del cliente

*Contexto*: al ser el código open source, se planteó proteger el flujo
OAuth con una comprobación de hash del código cliente antes de permitir
su ejecución.

*Decisión*: no implementar esa protección.

*Justificación*: en software open source, cualquier comprobación que
viva en el mismo código que se distribuye es evadible por quien
controla el entorno de ejecución (comentar la comprobación, recalcular
el hash esperado, ejecutar con depurador). El límite de confianza real
del sistema es el servidor de autorización OAuth de cada plataforma, no
el código propio: ninguna modificación del cliente permite obtener un
`access_token` sin el consentimiento explícito del titular de la cuenta
en la pantalla de la propia plataforma.

*Consecuencias*: (+) se evita invertir esfuerzo en una protección
inefectiva y fácilmente cuestionable ante un tribunal técnico; (+) la
memoria puede argumentar correctamente dónde está el verdadero límite
de confianza del sistema.

=== ADR-6: Rangos de versión en vez de versiones exactas

*Contexto*: varias roturas de entorno (numpy sin wheel para la versión
de Python del desarrollador, luego `pydantic_core`/`fastapi` con Python
3.14, y efectos en cadena sobre `respx` y
`prometheus-fastapi-instrumentator`).

*Decisión*: `requirements.txt`/`requirements-dev.txt` usan rangos
(`>=x,<y`) en vez de pines exactos.

*Consecuencias*: (+) resiliencia frente a distintas versiones de Python
entre máquinas de desarrollo y el runner de CI; (-) build ligeramente
menos determinista (dos instalaciones en momentos distintos pueden
resolver versiones exactas distintas dentro del rango).

=== ADR-7: Reutilización del monorepo de la asignatura ASW

*Contexto*: la plantilla `yovi_en1b` (Uniovi) ya traía Docker Compose,
Prometheus/Grafana, GitHub Actions y SonarCloud configurados.

*Decisión*: partir de ese repositorio, eliminando el servicio `gamey`
(Rust, ajeno al TFG) y sustituyendo el contenido de `users/` (antes
Node) por el backend Python. La carpeta se mantuvo con el nombre
heredado (`users/`) durante buena parte del desarrollo -- coste de
oportunidad aceptado frente a tocar Docker Compose, CI y SonarCloud
antes de que el resto del proyecto estuviera estable -- y se renombró a
`backend/` más adelante, actualizando esas mismas piezas de golpe.

*Consecuencias*: (+) ahorro significativo de tiempo de configuración de
infraestructura; (-) necesidad de mantener consistencia de convenciones
heredadas (nombres de servicios, puertos, estructura de carpetas) aunque
el dominio del proyecto no tenga relación con el original; (-) el
rename posterior tuvo que tocar simultáneamente `docker-compose.yml`, dos
workflows de GitHub Actions, `sonar-project.properties`, `.gitignore` y
la configuración de Prometheus -- todos los sitios que hacían referencia
literal a la carpeta por nombre, un recordatorio de que ese acoplamiento
disperso tiene coste real cuando llega el momento de deshacerlo.

=== ADR-8: Estimación de k-anonimato con proporciones agregadas del INE, no una base de datos sintética

*Contexto*: se necesitaba mostrar al usuario "cuánta gente comparte tus
características autodeclaradas" (edad, sexo, provincia, estudios...),
al estilo de una tabla de k-anonimato clásica.

*Alternativas consideradas*: construir una base de datos sintética con
una fila por cada uno de los ~49 millones de habitantes de España
(poblada a partir de Censo/Padrón/microdatos del INE) y resolver la
consulta con un `SELECT COUNT(*) ... WHERE ...` real.

*Decisión*: multiplicar en cadena proporciones agregadas del INE
(`data/ine_reference.py`), asumiendo independencia estadística entre
atributos, en vez de materializar microdatos sintéticos.

*Consecuencias*: (+) coherente con el principio "sin persistencia" que
sostiene el resto del argumentario RGPD del proyecto; (+) trivial de
auditar (cada número del informe se puede rastrear a una multiplicación
concreta); (+) no requiere procesar microdatos reales del INE (formato
de registro fijo, no trivial de tratar); (-) menos preciso que microdatos
reales en los casos donde hay correlación real entre atributos (p. ej.
la distribución de edad no es exactamente igual en todas las provincias)
— limitación documentada explícitamente en el propio informe.

=== ADR-9: Geolocalización de fotos limitada a España y a nivel de provincia

*Contexto*: se planteó geolocalizar fotos de Instagram al estilo de
herramientas comerciales tipo GeoSpy.

*Alternativas consideradas*: replicar un índice de geolocalización
mundial (inviable: requiere cientos de millones de imágenes
georreferenciadas e infraestructura fuera del alcance de un TFG);
predecir coordenadas GPS exactas (poco realista: incluso el estado del
arte publicado solo acierta la calle/1km ~26-29% de las veces).

*Decisión*: DINOv2 (extracción de embeddings) + FAISS (búsqueda de
vecinos más cercanos) contra un índice construido únicamente con
imágenes de España (subconjunto filtrado del dataset público OSV-5M), y
la predicción se agrega a nivel de **provincia**, no de coordenadas
exactas.

*Consecuencias*: (+) índice manejable en recursos de un TFG (varios GB
en vez de un dataset mundial); (+) mayor precisión relativa al competir
en un espacio de búsqueda más pequeño; (+) la granularidad de provincia
coincide con la que ya usa el módulo de k-anonimato, integrándose de
forma natural en el resto del informe; (-) no compite en precisión con
herramientas comerciales que sí tienen infraestructura e índices
mundiales propietarios — limitación reconocida y documentada, no
ocultada.

=== ADR-10: Mistral AI como proveedor de análisis con IA, por jurisdicción

*Contexto*: se quería una función opcional para que un LLM leyera el
informe ya generado y diera conclusiones en lenguaje natural. Se
valoraron varios proveedores baratos, incluido DeepSeek.

*Alternativas consideradas*: DeepSeek (más barato, pero empresa china:
implica una transferencia internacional de datos personales fuera del
Espacio Económico Europeo, con las obligaciones adicionales del RGPD
Capítulo V que eso conlleva); modelo propio entrenado/fine-tuned
localmente (descartado: coste de entrenamiento y de generación de
dataset desproporcionado para una tarea de razonamiento en contexto
sobre datos ya estructurados, que no requiere especialización de
dominio).

*Decisión*: Mistral AI (La Plateforme), tier gratuito, empresa con sede
en Francia.

*Consecuencias*: (+) evita justificar una transferencia internacional de
datos personales, al procesarse dentro de la UE; (+) sin coste (tier
gratuito, con degradación explícita si se agota la cuota, sin
reintentos); (-) calidad de respuesta algo menor que la de modelos de
proveedores más caros según benchmarks públicos, aceptado como
compromiso razonable para una función complementaria opcional.

*Nota*: este mismo razonamiento de jurisdicción aplicó también, sin
volver a discutirlo desde cero, cuando se añadió una segunda integración
independiente con el mismo proveedor (`nlp/ai_attribute_extraction.py`,
ver ADR-13) que envía texto/bio públicos en vez de un informe ya
agregado.

=== ADR-11: Progreso en vivo vía Server-Sent Events, no polling ni WebSockets

*Contexto*: el análisis completo (sobre todo con geolocalización de
fotos activada) puede tardar varios segundos; se quería sustituir la
espera opaca por una pantalla de progreso real.

*Alternativas consideradas*: *polling* periódico desde el frontend
(añade latencia y carga innecesaria); WebSockets (bidireccional,
más complejo de lo que este caso de uso necesita, ya que el servidor
nunca necesita recibir datos del cliente durante el análisis).

*Decisión*: Server-Sent Events (`GET /api/analyze/{platform}/stream`),
unidireccional servidor->cliente, con eventos JSON (`{"done": false,
"stage": "...", ...}` en curso, `{"done": true, "report": {...}}` o
`{"done": true, "error": "..."}` al terminar). El endpoint clásico
(`POST /api/analyze/{platform}`) se mantiene sin cambios para
compatibilidad y para los tests existentes.

*Consecuencias*: (+) hitos de progreso REALES (cada evento corresponde a
un paso del pipeline que de verdad acaba de terminar, no a un
temporizador simulado); (+) más simple de implementar y depurar que
WebSockets para un flujo unidireccional; (-) dos endpoints distintos
para la misma lógica de negocio (`_build_report` compartido entre
ambos, para no duplicar la orquestación).

=== ADR-12: Webapp y backend bajo el mismo origen (proxy de Nginx), en vez de `VITE_API_URL` absoluto

*Contexto*: en desarrollo local con un túnel rápido de Cloudflare
(`trycloudflare.com`, gratuito) para poder probar el login de Instagram
(que exige `redirect_uri` HTTPS), la webapp y el backend vivían en
dominios distintos. Cada reinicio del túnel generaba una URL nueva que
había que propagar manualmente a tres sitios: `INSTAGRAM_REDIRECT_URI`,
el panel de Meta for Developers, y `VITE_API_URL` de la webapp.

*Alternativas consideradas*: automatizar la propagación de la URL nueva
con un script que reescribiera `.env` y reconstruyera la webapp en cada
reinicio del túnel (descartado: sigue exigiendo un paso manual en Meta,
que no tiene API para gestionar su lista de redirect URIs válidos, así
que la automatización no eliminaba el cuello de botella real, solo lo
desplazaba); usar un túnel con nombre/persistente de Cloudflare
(descartado por el momento: exige un dominio propio en Cloudflare, fuera
del alcance gratuito del proyecto).

*Decisión*: servir la webapp y el backend bajo un único origen. El
Nginx de la imagen de la webapp hace de proxy inverso hacia el backend
(`/auth/*`, `/api/*`) bajo el mismo dominio de cara al navegador; la
webapp se construye con `VITE_API_URL` vacío (rutas relativas). El
`redirect_uri` de Instagram y el destino de la redirección final tras el
login se derivan del header `Host` de la petición entrante cuando no hay
un valor fijo en `.env` (`auth/dynamic_origin.py`).

*Consecuencias*: (+) un único túnel apuntando al puerto de la webapp
sirve también, transparentemente, la autenticación y la API; (+) solo
queda un paso manual (dar de alta la URL en Meta), no tres sitios que
sincronizar; (+) el mismo mecanismo simplifica también producción (ya no
hace falta un `DEPLOY_HOST` para construir la imagen de la webapp,
Docker resuelve `backend` por DNS interno igual en local que
desplegado); (-) la derivación dinámica solo es correcta cuando webapp y
backend comparten origen de verdad -- documentado explícitamente para no
asumir por error que sirve también para desarrollo sin Docker con
puertos distintos (`npm run dev` + `uvicorn` sueltos).

=== ADR-13: Extracción de atributos con IA como complemento de las regex, nunca sustituto

*Contexto*: las regex de `demographic_extraction.py` tienen un
vocabulario fijo ("estudio X", "estudiante de X"...); cualquier
redacción real que no encaje se pierde en silencio (p. ej. "voy a 2º de
Enfermería").

*Alternativas consideradas*: sustituir las regex por extracción vía IA
por completo (descartado: perdería la garantía de coincidencia exacta y
determinista que ya funcionaba bien, y encarecería/ralentizaría el
análisis incluso para los casos que las regex ya resolvían gratis);
pedir a la IA que decidiera directamente la categoría del INE
correspondiente (descartado: una alucinación del modelo podría colar una
categoría inventada como si fuera una estimación de población real).

*Decisión*: `nlp/ai_attribute_extraction.py` corre siempre después de
las regex y solo rellena los campos que estas no encontraron
(`merge_findings`, con las regex teniendo prioridad). El LLM solo
propone texto libre; la normalización final contra las tablas del INE
la sigue haciendo el propio código, igual que para las regex. Además,
propone por separado una estimación de sexo por convención cultural del
nombre público de la cuenta, marcada con una procedencia distinta
(`ia_nombre`) y una nota de menor fiabilidad explícita en el informe --
nunca se mezcla con una autodeclaración real en el mismo nivel de
confianza.

*Consecuencias*: (+) capta redacciones libres sin perder la
trazabilidad ni la resistencia a alucinaciones del enfoque por regex;
(+) coherente con el principio de explicabilidad del resto del proyecto
(ver <<section-concepts>>); (-) el análisis ahora depende, para esta
mejora concreta, de una llamada de red adicional a un tercero (Mistral),
mitigado por ser opcional y degradarse con gracia sin `MISTRAL_API_KEY`.

=== ADR-14: Análisis del informe con IA disparado automáticamente, no bajo demanda

*Contexto*: la primera versión exigía que el usuario pulsara
explícitamente "Analizar con IA" tras ver el informe.

*Decisión*: se dispara solo, en cuanto el informe principal está
disponible, sin confirmación adicional del usuario.

*Justificación*: el consentimiento OAuth inicial ya cubre todo el
análisis que la herramienta hace sobre la cuenta del usuario; un botón
adicional para una llamada que solo envía agregados ya generados (nunca
las publicaciones originales) no añadía ninguna protección de privacidad
real, solo fricción de interfaz. La función sigue siendo aislada y
opcional en caso de fallo (sin `MISTRAL_API_KEY`, o si Mistral no
responde, el resto del informe no se ve afectado) -- lo único que
cambió es cuándo se dispara, no las garantías de degradación.

*Consecuencias*: (+) el usuario ve el veredicto y las conclusiones sin
un paso extra; (-) una llamada más a Mistral en cada análisis (incluso
si el usuario no llega a mirar esa sección), aceptado por ser
gratuita/de bajo coste y por degradarse sin romper nada si falla.

=== ADR-15: Dependencias de geolocalización activables por build-arg, con precarga en el arranque

*Contexto*: `torch`/`faiss`/`transformers` no estaban en
`requirements.txt` bajo la premisa de que "solo hacen falta para
construir el índice" (un script que se corre aparte, no en el backend
desplegado). Esa premisa resultó ser incorrecta: el propio análisis en
producción también necesita esas librerías para calcular el embedding de
cada foto del usuario y consultar el índice ya construido -- sin ellas
en la imagen del backend, la función se reporta como "no disponible"
aunque el índice exista y esté montado correctamente.

*Alternativas consideradas*: instalarlas siempre en `requirements.txt`
(descartado por defecto: cientos de MB extra en instalaciones que no
usan Instagram o no quieren geolocalización); mantener el bug
implícitamente y limitarse a documentar "esta función requiere pasos
adicionales que no automatizamos" (descartado: no es coherente con el
resto del proyecto, que sí tiene la ambición de que los módulos
opcionales se activen limpiamente).

*Decisión*: `requirements-vision.txt` aparte, instalado en la imagen
Docker solo si se construye con `--build-arg WITH_GEOLOCATION=true`
(activado por defecto en `docker-compose.yml`), usando el índice de
PyTorch solo-CPU (más ligero que el paquete de PyPI por defecto, que
incluye CUDA). El modelo y el índice se precargan en el `lifespan` de
FastAPI al arrancar el contenedor, no en la primera petición de
análisis, y la caché de los pesos del modelo se persiste en un volumen
para no volver a descargarlos en cada reinicio.

*Consecuencias*: (+) instalaciones sin geolocalización siguen siendo
ligeras; (+) el primer usuario en analizar una cuenta de Instagram tras
un despliegue no paga el coste de cargar el modelo; (+) el modelo no se
vuelve a descargar en cada reinicio del contenedor; (-) activar
geolocalización añade varios minutos a la primera construcción de la
imagen (descarga de `torch`), mitigado con timeouts/reintentos más
generosos en `pip` para conexiones lentas.
