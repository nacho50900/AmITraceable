[[section-building-block-view]]
== Vista de bloques de construcción

=== Caja blanca: sistema completo

[source]
----
+-------------------------------------------------------------+
|                        AmITraceable                         |
|                                                               |
|  +------------------+        +---------------------------+  |
|  |     webapp       | <----> |          backend          |  |
|  |  React + TS SPA  |  HTTP  |  FastAPI (Python)          |  |
|  |  + Nginx (proxy) |  interno (Docker)                   |  |
|  +------------------+        +---------------------------+  |
|         ^                          |          |             |
|         | HTTPS (mismo origen      |          |              |
|         |  de cara al navegador)   |          |              |
|    [ Navegador ]              Prometheus     Reddit /         |
|                                (/metrics)     Instagram APIs   |
+-------------------------------------------------------------+
----

Motivación::
Separación clásica frontend/backend. El backend es agnóstico de
plataforma de despliegue (se ejecuta igual en local, en Docker o en el
runner de CI); el frontend es una SPA estática servida por Nginx en
producción, y ese mismo Nginx hace de proxy hacia el backend bajo un
único origen (ver ADR-12 y <<section-solution-strategy>>) -- de cara al
navegador, webapp y backend son indistinguibles, viven en el mismo
dominio.

Bloques contenidos::
[cols="1,2", options="header"]
|===
| Bloque | Responsabilidad

| `webapp`
| Interfaz de usuario: pantalla de consentimiento/selección de
  plataforma y dashboard del informe de exposición. Su Nginx también
  actúa de proxy inverso hacia `backend`.

| `backend`
| Lógica de dominio completa: OAuth por plataforma, extracción de datos,
  fingerprinting, inferencia de atributos, scoring, generación del
  informe.

| Prometheus / Grafana
| Observabilidad: métricas HTTP del backend y dashboards.
|===

Interfaces importantes::
* Navegador -> `webapp` (Nginx) -> `backend`: API REST/JSON documentada
  automáticamente por FastAPI en `/docs` (OpenAPI); el navegador solo ve
  un origen, Nginx reenvía internamente por `/auth/*` y `/api/*`.
* `backend` -> Reddit/Instagram: APIs OAuth 2.0 oficiales de cada
  plataforma (ver <<section-context-and-scope>>).

==== `auth/{platform}_oauth.py`

Propósito/Responsabilidad::
Flujo OAuth 2.0 completo de una plataforma: redirección a autorización,
canje de `code` por `access_token` (con paso intermedio de canje a token
de larga duración en el caso de Instagram), almacenamiento en cookie de
sesión firmada, y endpoints de `logout`/`status`.

Interfaces::
`GET /auth/{platform}/login`, `GET /auth/{platform}/callback`,
`POST /auth/{platform}/logout`, `GET /auth/{platform}/status`.

Características de calidad::
Sin persistencia; validación de `state` contra CSRF; claves de sesión
con prefijo de plataforma (`reddit_oauth_state`, `instagram_oauth_state`)
para que ambas puedan coexistir sin colisión. El `redirect_uri` de
Instagram usa `dynamic_origin.py` cuando no hay un valor fijo en `.env`
(ver más abajo).

Ubicación::
`backend/app/auth/reddit_oauth.py`, `backend/app/auth/instagram_oauth.py`.

==== `auth/dynamic_origin.py`

Propósito/Responsabilidad::
Deriva el `redirect_uri` de Instagram y la URL final a la que redirigir
tras un login (correcto o denegado) a partir del header `Host` de la
propia petición, cuando no hay un valor fijo configurado en `.env`.
Pensado para desarrollo local con túneles rápidos de Cloudflare
(`trycloudflare.com`), cuya URL cambia en cada reinicio del túnel --
sin esto, habría que editar `.env` y reiniciar el proceso cada vez.
Solo es correcto porque webapp y backend viven bajo el mismo origen (ver
Nivel 1 más arriba); si se sirvieran en dominios distintos sin proxy de
por medio, esta derivación daría un resultado incorrecto para el destino
de la redirección final (no para el `redirect_uri` de Instagram, que
siempre es el propio backend).

Interfaces::
`current_origin(request)`, `frontend_target(request, configured)`,
usadas por ambos módulos de OAuth.

Ubicación::
`backend/app/auth/dynamic_origin.py`.

==== `{platform}_client.py`

Propósito/Responsabilidad::
Extraer los datos públicos de la cuenta autenticada y normalizarlos al
modelo genérico `SocialProfile`/`SocialPost`. Aplica el principio de
minimización de datos: solo se piden los campos necesarios para el
análisis.

En Instagram, un post tipo carrusel (`CAROUSEL_ALBUM`) puede traer varias
imágenes; `instagram_client.py` pide explícitamente el campo `children`
de la API y extrae TODAS las imágenes del carrusel, no solo la primera
-- así `vision/geolocation.py` y `vision/scene_analysis.py` analizan cada
imagen del carrusel por separado, en vez de perder la información de las
demás. Cada foto de un carrusel recibe además su propio enlace
(`?img_index=N`, ver `_photo_link()` en `geolocation.py`) en vez de que
todas apunten al mismo permalink de la publicación -- necesario también
para que las descripciones visuales de cada foto no se sobrescriban entre
sí (bug real corregido, ver ADR-23 en <<section-design-decisions>>).

Interfaces::
Clase `RedditClient`/`InstagramClient` con método asíncrono
`fetch_profile() -> SocialProfile`.

Ubicación::
`backend/app/reddit_client.py`, `backend/app/instagram_client.py`.

==== `analysis_router.py`

Propósito/Responsabilidad::
Orquesta el pipeline común (fingerprint -> inferencia -> scoring ->
informe) para cualquier plataforma registrada. Resuelve el cliente
correspondiente a partir de la sesión mediante un diccionario de
factories (`_PLATFORM_CLIENT_FACTORIES`), sin lógica condicional
especial por plataforma en el cuerpo del endpoint. Expone tres variantes
del mismo análisis:

* `POST /api/analyze/{platform}` -- variante síncrona clásica, responde
  con el `ExposureReport` completo al terminar.
* `GET /api/analyze/{platform}/stream` -- misma lógica vía Server-Sent
  Events, emitiendo hitos de progreso reales ("Leyendo publicaciones...",
  "Analizando fotos...", con contadores) a medida que el pipeline los
  completa. Es la variante que usa el frontend (`Dashboard.tsx`, vía
  `EventSource`) para la pantalla de progreso en vivo.
* `POST /api/analyze/ai-summary` -- endpoint aislado del pipeline
  principal: recibe un `ExposureReport` ya generado y lo reenvía a
  `ai_analysis.py`. Se dispara automáticamente desde el frontend en
  cuanto el informe está listo, sin acción explícita del usuario.
* `POST /api/analyze/recalculate` -- recibe un `ExposureReport` ya
  generado más una lista de `ManualAttribute` (rasgos físicos que la
  ley de protección de datos impide inferir automáticamente: color de
  ojos/pelo/piel -- ver ADR-34 y `PopulationNarrowingTable.tsx` en la
  vista de `webapp` más abajo) y devuelve el mismo informe con esos
  rasgos añadidos a `inferred_attributes`, el `population_narrowing`
  encadenado con las nuevas proporciones (`data/ine_reference.py`:
  `EYE_COLOR_DISTRIBUTION`, `HAIR_COLOR_DISTRIBUTION`,
  `SKIN_TONE_DISTRIBUTION`) y `privacy_score.inferable_data_risk`/
  `overall_score` recalculados. Reutiliza `_apply_proportion` y
  `final_remaining_population` de `scoring/k_anonymity.py`, la misma
  lógica que usa el pipeline automático -- evita duplicar las tablas
  del INE ni el cálculo de k-anonimato en el frontend.
+
IMPORTANT: esta ruta está registrada **antes** que
`POST /api/analyze/{platform}` en el código fuente. FastAPI/Starlette
resuelve las rutas en el orden de registro: si `{platform}` fuera
antes, capturaría el literal `"recalculate"` como valor de ese
parámetro y la ruta de recalculo nunca se alcanzaría (404 encubierto,
"Plataforma no soportada: recalculate"). Cualquier ruta estática nueva
bajo `/analyze/` debe declararse antes que la ruta paramétrica por el
mismo motivo.

Interfaces::
Ver arriba. Todos documentados con sus posibles códigos de respuesta en
`/docs` (OpenAPI).

Ubicación::
`backend/app/analysis_router.py`.

==== `nlp/fingerprint.py`

Propósito/Responsabilidad::
Calcula longitud media de frase, riqueza de vocabulario (type-token
ratio), tasa de uso de emojis, distribución horaria de actividad,
comunidades/etiquetas más frecuentes (`top_groups`), keywords (TF-IDF) e
idioma detectado.

Ubicación::
`backend/app/nlp/fingerprint.py`.

==== `nlp/attribute_inference.py`

Propósito/Responsabilidad::
Heurísticas explicables (listas curadas + regex) para inferir
ubicación, ocupación y rutina, cada una con nivel de confianza y
evidencia (permalinks).

Ubicación::
`backend/app/nlp/attribute_inference.py`.

==== `nlp/demographic_extraction.py`

Propósito/Responsabilidad::
Detecta declaraciones EXPLÍCITAS que el propio usuario hace sobre sí
mismo en su texto ("tengo 24 años", "vivo en León", "estudio Medicina"),
mediante regex, distinto de `attribute_inference.py` (que infiere de
forma indirecta a partir de en qué comunidades participa). Alimenta el
estimador de k-anonimato. Se ejecuta siempre primero, y tiene prioridad
sobre lo que encuentre `ai_attribute_extraction.py` para el mismo campo.

La ubicación se detecta con jerarquía municipio > provincia > comunidad
autónoma: si el texto da un municipio o provincia exacta del INE, se usa
esa (más específico); si solo da el nombre de una comunidad autónoma
completa ("vivo en Canarias", "vivo en Andalucía"), sin poder elegir
provincia, se guarda a nivel de comunidad -- salvo que esa comunidad
tenga una única provincia (Asturias, Madrid, Murcia...), en cuyo caso no
hay ambigüedad y se resuelve directamente a esa provincia.

El `DemographicFindings` que produce este módulo también reserva un
campo `estado_civil` (soltero/con_pareja/casado/viudo), pero a
diferencia del resto de campos de esta clase, la propia regex NUNCA lo
rellena: no hay una autodeclaración explícita equivalente a "tengo 24
años" para el estado civil que valga la pena cazar por regex. Lo
rellenan `ai_attribute_extraction.py` (razonamiento simbólico sobre
texto) o `report/generator.py` (señal de pareja detectada en fotos, ver
`vision/scene_analysis.py`) -- este módulo solo define el campo para que
ambos tengan un sitio común donde escribirlo.

`practica_deportiva` (41 modalidades, `_SPORT_PRACTICE_RE`) exige una
frase-ancla de PRÁCTICA en primera persona ("juego al...", "hago...",
"practico...") -- una simple mención del deporte ("vi el partido de
fútbol") no cuenta, es mucho más frecuente en redes sociales que una
autodeclaración real y colaría un falso positivo. Cuando la frase-ancla
de una modalidad es literalmente un PREFIJO de la de otra ("tenis"
dentro de "tenis de mesa", "fútbol" dentro de "fútbol sala", "esquí"
dentro de "esquí náutico"), el orden de alternancia del regex importa:
la más específica va siempre primero, o la más genérica capturaría el
match antes de llegar a probar la correcta.

`nivel_estudios` (superior / secundaria_superior / secundaria_o_inferior,
clasificación CNED-2014/ISCED del INE) es DISTINTO de `estudios` (la
carrera universitaria concreta, más abajo): exige haber COMPLETADO ese
nivel ("tengo el bachillerato", no "estoy estudiando bachillerato"), y
se infiere automáticamente como `superior` si `estudios` ya detectó una
carrera nombrada, sin necesitar su propia frase-ancla. Los Ciclos
Formativos de FP son el caso delicado: un Grado SUPERIOR cuenta como
`superior` (nivel 5 en la clasificación del INE, igual que la
universidad), mientras que un Grado MEDIO cae en
`secundaria_superior` -- de ahí que las frases-ancla exijan
"superior"/"medio" explícito en vez de un "ciclo formativo" genérico
sin cualificar.

`rama_estudios` (Ciencias Sociales y Jurídicas / Ingeniería y
Arquitectura / Ciencias de la Salud / Artes y Humanidades / Ciencias,
clasificación oficial del RD 1393/2007) es DISTINTO de ambos: ni el
nivel alcanzado ni la carrera concreta, sino la categoría amplia a la
que pertenece esa carrera (ver ADR-40). Se infiere automáticamente vía
`STUDIES_TO_RAMA` cuando `estudios` ya detectó una de las 14 carreras
con proporción propia, pero también tiene su propio vocabulario
AMPLIADO (~25 carreras más: sociología, filología, física...) que
reutiliza la misma frase-ancla que `estudios` (`_STUDY_VERB_RE`) contra
un diccionario más amplio, para cubrir carreras que `estudios` no tiene
registradas individualmente. Cuando una carrera queda contenida como
substring de otra ("quimica" dentro de "ingenieria quimica", "historia"
dentro de "historia del arte"), aplica la misma regla de orden que
`_SPORT_PRACTICE_RE`: la más específica se comprueba primero.

Ubicación::
`backend/app/nlp/demographic_extraction.py`.

==== `nlp/ai_attribute_extraction.py` (opcional)

Propósito/Responsabilidad::
La misma extracción que `demographic_extraction.py`, pero vía un modelo
de lenguaje (Mistral, opcional): capta redacciones libres que el
vocabulario fijo de las regex no reconoce (p. ej. "voy a 2º de
Enfermería"). Solo rellena campos que la regex no encontró -- nunca los
sustituye, para no perder la garantía de coincidencia exacta cuando
existe. También propone, por separado, una estimación de sexo por
convención cultural del nombre público de la cuenta (`sexo_por_nombre`
en el JSON del modelo), marcada con una procedencia distinta
(`ia_nombre`) y menor fiabilidad explícita que una autodeclaración real
-- nunca se mezclan en el mismo nivel de confianza. El LLM nunca decide a
qué categoría del INE pertenece un valor: solo propone el texto libre,
que se normaliza contra las tablas de `ine_reference.py` igual que hace
la regex, para que un valor alucinado simplemente no encuentre
coincidencia en vez de colar una estimación de población falsa. Al igual
que la regex, detecta comunidad autónoma completa como campo aparte
(`comunidad_autonoma`) cuando no hay municipio/provincia concreta.

En el mismo pase (sin llamada adicional al modelo), también marca qué
publicaciones tienen pinta de ser "de viaje/vacaciones" (campo
`fotos_de_viaje` del JSON) -- señal que usa `report/generator.py` para
no confundir "dónde fue tomada esta foto" con "dónde vive esta persona"
al combinarlo con la geolocalización de imagen (ver
`nlp/travel_detection.py`, su equivalente por regex).

También, en el mismo pase, propone un `estado_civil` (soltero /
con_pareja / casado / viudo) razonando sobre contenido simbólico o
indirecto del texto -- nunca una autodeclaración explícita como las de
`demographic_extraction.py` -- por ejemplo, una bio con fecha y emojis de
pareja, o una publicación que mencione "mi marido". Se marca con
`source["estado_civil"] = "ia_simbolica"` (nunca `"texto"` ni `"ia"` a
secas) para que el informe deje claro que es una inferencia de fiabilidad
menor que una autodeclaración real. Si ni el texto ni este razonamiento
simbólico dan nada, `report/generator.py` todavía puede rellenar el
mismo campo a partir de una señal de pareja detectada en fotos (ver
`vision/scene_analysis.py`), con `source = "imagen"` en ese caso.

Con el mismo tipo de razonamiento indirecto, este módulo también puede
rellenar `edad_rango_min`/`edad_rango_max` (un RANGO de edad, de ANCHO
LIBRE -- no un tramo quinquenal fijo del INE) cuando
`demographic_extraction.py` NO encontró una edad exacta autodeclarada
-- pistas como un año de graduación, el curso que la persona menciona
estar haciendo o referencias generacionales. El prompt le pide
explícitamente al modelo ENSANCHAR el rango cuando la pista sea débil,
en vez de arriesgarse a un valor puntual que no pueda justificar: un
rango de 20 años con confianza alta es preferible a uno estrecho con
confianza baja. `_set_edad_rango` descarta la estimación por completo
si la confianza declarada no supera 0.7 (ver
`ai_attribute_extraction.py::_AGE_RANGE_MIN_CONFIDENCE`) -- ante la
duda, no se adivina, ni siquiera por rango amplio -- y, si se acepta,
guarda `edad_rango_min`/`edad_rango_max` tal cual y la confianza en
`DemographicFindings.confidence["edad_rango_min"]` (duplicada también
bajo `"edad_rango_max"` para que el mecanismo genérico de merge por
nombre de campo la traspase sin caso especial). La proporción de
población de ese rango se calcula sumando `AGE_DISTRIBUTION_1Y` año a
año (`ine_reference.age_range_proportion`), no encajándolo en un tramo
prefijado -- así, ensanchar el rango nunca produce una falsa precisión,
solo reduce menos la población (ver ADR-27, actualización de agosto de
2026: el mecanismo original pedía una edad puntual con un umbral de
confianza como única defensa, y se coló una estimación de 30 años para
alguien de 21 real). Se marca igual que `estado_civil` con una
procedencia distinta (`source["edad_rango_min"] = "ia_estimada"`, nunca
`"ia"` a secas) y nunca sustituye una edad exacta ya conocida, sea de
regex o de la propia IA (ver ADR-27).

Interfaces::
`extract_demographics_with_ai(posts, username, full_name, bio)`,
`merge_findings(regex_findings, ai_findings)`.

Ubicación::
`backend/app/nlp/ai_attribute_extraction.py`.

==== `nlp/travel_detection.py`

Propósito/Responsabilidad::
Detección por regex (determinista, gratuita, sin IA) de publicaciones
cuyo texto indica que la persona está de viaje/vacaciones/de paso por un
sitio ("de viaje en Roma", "unos días en la playa"). Es la red de
seguridad de `ai_attribute_extraction.py` (campo `fotos_de_viaje`):
funciona siempre, incluso sin `MISTRAL_API_KEY`. Las dos fuentes se UNEN,
nunca se sustituyen -- un falso positivo aquí (excluir una foto que sí es
de casa) es mucho menos grave que un falso negativo (usar una foto de
vacaciones para "inferir" dónde vive la persona), así que ambas listas se
combinan sin más criterio que "si cualquiera de las dos lo marca, se
excluye".

Interfaces::
`detect_travel_permalinks(posts) -> set[str]`.

Ubicación::
`backend/app/nlp/travel_detection.py`.

==== `scoring/k_anonymity.py`

Propósito/Responsabilidad::
Estima, para cada declaración detectada (por regex o por IA), cuánta
población en España comparte esa combinación de características (ver
<<section-concepts>>, "Estimación de k-anonimato sin base de datos
sintética"). Devuelve una cascada de pasos (`PopulationNarrowingStep`)
con la población restante, nivel de riesgo, fuente (texto / imagen / ia
/ ia_nombre / ia_simbolica / **manual** -- ver más abajo) y la
proporción ya calculada sobre el total de España (para que el frontend
pueda representarla visualmente sin conocer esa constante). Cada paso
incluye además `reduction_percent`
-- cuánto reduce ESE rasgo concreto la población restante respecto al
paso anterior de la cadena (no el porcentaje acumulado desde el
principio) -- que la tabla de estrechamiento de población muestra junto
a cada fila.

El paso de ubicación tiene tres niveles de granularidad, de más a menos
específico: municipio > provincia > **comunidad autónoma**. El tercer
nivel existe porque tanto la geolocalización por imagen (a veces solo
identifica la comunidad, no una provincia concreta -- p. ej. Canarias)
como una autodeclaración de texto tipo "vivo en Andalucía" no permiten
elegir una sola provincia sin inventar información; usa
`CCAA_POPULATION` (`ine_reference.py`), calculada sumando la población
de las provincias de cada comunidad.

`final_remaining_population(steps)` calcula, aparte, la población que
comparte TODOS los rasgos encadenables a la vez (sexo + edad + ubicación
+ estudios + ocupación combinados, no uno aislado) -- es el número que
se muestra al final del informe ("En España hay X personas que comparten
tus rasgos"). Se queda con el `remaining_population` del último escalón
encadenable que sí se pudo estimar, aprovechando que cada escalón ya
lleva el acumulado de los anteriores.

El paso de `practica_deportiva` (41 modalidades, ver ADR-37) consulta
OTROS campos de `findings` además del suyo propio (no es el único, ver
`rama_estudios` más abajo): si ya se conoce sexo, edad o nivel_estudios,
usa la proporción de esa combinación concreta
(`SPORT_PRACTICE_BY_SEX`/`BY_AGE_BAND`/`BY_EDUCATION_LEVEL` en
`ine_reference.py`, tabla 1.22 de la encuesta) en vez de la marginal sin
distinguir. Prueba las tres en cascada -- sexo > edad > nivel_estudios --
y usa la PRIMERA que esté disponible y tenga dato para esa combinación
concreta; nunca combina dos ajustes a la vez (no existe un cruce a
cuatro bandas simultáneo en la encuesta, solo tres cruces independientes
de a uno). Un rango de edad declarado que cruza la frontera entre dos
tramos de la encuesta (`_sport_age_band`) no se puede asignar a ninguno
sin adivinar, así que cuenta como "no disponible" para ese nivel de la
cascada.

El paso de `rama_estudios` (ver ADR-40) también consulta otro campo,
pero al revés que `practica_deportiva`: en vez de AFINAR la proporción
cuando otro campo ya se conoce, se SALTA por completo si `estudios` ya
está informado. La razón es que, a diferencia de sexo/edad/estudios
(variables independientes entre sí que aportan señal adicional cada
una), "estudia derecho" y "está en la rama Ciencias Sociales y
Jurídicas" no son hechos independientes -- el segundo es una
consecuencia exacta del primero. Aplicar la proporción de la rama
ENCIMA de la proporción de la carrera concreta contaría el mismo hecho
dos veces. El campo `rama_estudios` se sigue rellenando igualmente
(para mostrarlo en el resto del pipeline), solo se omite el paso de
`population_narrowing` cuando sería redundante.

`source="manual"` (ADR-34) es el único caso en que un paso no lo genera
el pipeline automático de análisis, sino
`POST /api/analyze/recalculate` a partir de rasgos que el usuario
introduce a mano en el dashboard (color de ojos/pelo/piel -- protegidos
por ley y no inferibles automáticamente). Usa las mismas funciones
`_apply_proportion`/`final_remaining_population` que el resto de la
cadena, contra tres tablas nuevas de `ine_reference.py`
(`EYE_COLOR_DISTRIBUTION`, `HAIR_COLOR_DISTRIBUTION`,
`SKIN_TONE_DISTRIBUTION`) que son estimaciones contextuales, no cifras
oficiales del INE -- el INE no publica una distribución poblacional de
estos rasgos.

`AGE_DISTRIBUTION_1Y` (proporción de población por edad exacta, año a
año, usada por `age_range_proportion`) es DATO REAL del Censo (tabla
01003 del INE, año 2022), no una interpolación (ADR-36) -- antes se
derivaba repartiendo uniformemente `AGE_DISTRIBUTION_5Y` dentro de cada
tramo quinquenal, aproximación que llegó a dar tasas de práctica
deportiva por encima del 100% al cruzarla con tramos de edad estrechos.
Ahora la relación entre las dos tablas está invertida: `1Y` es la
fuente y `AGE_DISTRIBUTION_5Y` se deriva sumando `1Y` dentro de cada
tramo (`_build_age_distribution_5y_from_1y`), así que nunca pueden
desincronizarse entre sí.

Ubicación::
`backend/app/scoring/k_anonymity.py`, tablas en
`backend/app/data/ine_reference.py`.

==== `vision/geolocation.py` (opcional)

Propósito/Responsabilidad::
Estima la provincia (o, si la foto trae GPS real en su EXIF, la usa
directamente) más probable de una foto de Instagram por similitud visual
(DINOv2 + FAISS) contra un índice de imágenes georreferenciadas de
España (ver <<section-concepts>>). Módulo *best-effort*: devuelve TODAS
las estimaciones que consigue calcular, con su confianza real, sin
ocultar ninguna por umbral -- ese filtrado (para decidir si algo es lo
bastante fiable para alimentar el cálculo de k-anonimato) es
responsabilidad de `report/generator.py`, no de este módulo. Expone
además un flag independiente (`índice disponible`) para que el frontend
pueda distinguir "el índice no está construido, o faltan sus
dependencias" de "se analizaron fotos pero ninguna dio resultado
fiable" -- nunca se muestran los dos mensajes a la vez.

Dos comportamientos añadidos sobre la estimación por similitud visual
pura:

* **Atajo por GPS real (EXIF)**: si la foto trae coordenadas GPS en su
  EXIF, se usan directamente (se busca la región conocida más cercana a
  esas coordenadas) y NO se llama al modelo -- más barato y más fiable
  que cualquier estimación visual. En la práctica esto rara vez ocurre
  con fotos de Instagram, porque la plataforma elimina el EXIF al subir
  las imágenes; se implementa igualmente porque es gratis comprobarlo y
  deja de ser un caso muerto si se analiza otra fuente que sí conserve
  metadatos.
* **Fotos "no representativas"**: si los k vecinos más parecidos están
  geográficamente muy dispersos (media > 300 km entre ellos), la foto se
  marca con `representative=False` en vez de asignarle una provincia sin
  más -- una foto genérica (solo mar, solo cielo, un primer plano sin
  fondo distintivo...) puede parecerse visualmente a imágenes de
  referencia de medio país a la vez, así que ninguna provincia
  "ganadora" por mayoría simple sería significativa. La estimación
  sigue devolviéndose (con su confianza real, para el mapa), pero
  `report/generator.py` la excluye de la conclusión de residencia.

Además de la geolocalización en sí, este módulo es quien invoca
`vision/scene_analysis.py` (`analyze_image_content`) por cada foto: al
ser quien ya descarga la imagen para calcular su embedding, lanza ambos
análisis (geolocalización + contenido visual) sobre la misma descarga en
vez de que un segundo módulo tuviera que volver a pedirla. El resultado
de `scene_analysis.py` viaja como dos campos extra de
`GeolocationOutcome`: `visual_inferences` (aficiones/actividades, una
por foto y hallazgo, para sumarse a `inferred_attributes` en el informe)
y `partner_signal_permalinks` (permalinks donde se detectó una señal de
pareja, que `report/generator.py` usa para rellenar `estado_civil` si el
texto no dijo nada ya). Ver `vision/scene_analysis.py` para el detalle de
ese análisis.

Las dependencias pesadas (`torch`, `faiss`, `transformers`) están en
`requirements-vision.txt`, no en `requirements.txt`: no son solo para
poder construir el índice (`scripts/build_faiss_index.py`), también hacen
falta en el análisis en sí. La imagen Docker las instala solo si se
construye con `--build-arg WITH_GEOLOCATION=true`. El modelo y el índice
se precargan en el arranque del contenedor (`lifespan` en `main.py`), no
en la primera petición de análisis.

Interfaces::
`estimate_locations_for_posts(posts, progress_callback=None) ->
GeolocationOutcome`, llamado desde `report/generator.py` solo cuando
`platform == "instagram"`.

Ubicación::
`backend/app/vision/geolocation.py`, scripts de preparación del índice en
`backend/scripts/`.

==== `vision/scene_analysis.py` (opcional)

Propósito/Responsabilidad::
Analiza el CONTENIDO visual de cada foto de Instagram -- no *dónde* se
tomó (eso es `geolocation.py`), sino *qué hay* en ella -- mediante
Moondream2, un modelo de visión-lenguaje (VQA) pequeño (~1.8B parámetros)
que se ejecuta localmente vía `transformers`. Se le hacen DOS preguntas
separadas por foto, reutilizando la misma imagen ya codificada
(`_model.encode_image()`, sobre una copia redimensionada a 378px --
el `crop_size` real de esta revisión del modelo, ver ADR-22 en
<<section-design-decisions>> -- no la imagen a la resolución de 1024px
que usa DINOv2): un caption de texto libre EN INGLÉS (Moondream2 solo
tiene datos de entrenamiento en inglés) y una respuesta de formato fijo
en cuatro líneas (`PERSONAS`, `AFICION`, `PAREJA`, `TEXTO_VISIBLE`) en
ESPAÑOL, parseada como texto plano en vez de JSON estructurado -- los
modelos locales pequeños son mucho menos fiables generando JSON complejo
bien formado que uno grande. Mezclar ambos tipos de respuesta (texto
libre + opciones fijas) en un único prompt combinado provocaba que el
modelo copiara literalmente el ejemplo dado en vez de describir la
imagen real; separarlas en dos llamadas lo resolvió (ver ADR-21).

Límite ético/legal deliberado::
El modelo nunca debe identificar, nombrar, ni describir físicamente a
NINGUNA persona de la foto -- el consentimiento OAuth de este proyecto
cubre solo a la cuenta analizada; generar datos sobre la identidad de un
tercero sería tratar datos personales de alguien que nunca dio su
consentimiento. Lo único que se extrae son señales sobre la PROPIA cuenta
analizada (p. ej. "aparece en actitud romántica" -> indicio de que la
cuenta tiene pareja), nunca información sobre quién es la otra persona.
El campo `TEXTO_VISIBLE` (texto legible en la propia foto: carteles,
escaparates, nombres de lugares) tiene la misma restricción repetida
explícitamente en su propio prompt: nunca puede ser el nombre propio de
una persona, aunque se lea con claridad en una camiseta o insignia (ver
ADR-23).

Ambigüedad de varias personas en la misma foto::
El modelo no tiene forma de saber cuál de las personas de una foto es la
cuenta analizada -- es una imagen suelta, sin ninguna referencia externa
con la que comparar. Por eso el prompt pide explícitamente que declare
cuántas personas identifica como protagonistas (campo `PERSONAS`): con
una o ninguna, la señal de afición/actividad se atribuye a la cuenta
analizada con normalidad (mismo supuesto que ya asume el resto del
proyecto: que una autodeclaración en primera persona es sobre quien la
escribe). Con varias personas de protagonismo similar (p. ej. una
pareja), esa atribución dejaría de tener fundamento -- podría ser la otra
persona quien toca la guitarra de la foto, no la cuenta analizada -- así
que la señal de AFICIÓN se descarta en ese caso (`_parse_inferences`). La
señal de PAREJA, en cambio, no necesita resolver esa ambigüedad: da igual
cuál de las dos personas sea la cuenta analizada, el mero hecho de que la
cuenta publique una foto con contexto romántico ya es la señal, así que
esa sí se mantiene con varias personas. TEXTO_VISIBLE tampoco tiene este
problema: un cartel es verdad independientemente de quién salga en la
foto, es evidencia sobre el lugar/contexto, no un rasgo personal
atribuible a una persona concreta.

Integración con el resto del pipeline::
No se llama directamente desde `report/generator.py`: la invoca
`vision/geolocation.py` por cada foto (ver más arriba), que ya descarga
la imagen para su propio análisis y evita así una segunda descarga --
forzando la decodificación completa en el momento de la descarga
(`image.load()`), no de forma perezosa, porque DINOv2 y Moondream2 leen
la MISMA imagen en paralelo (ver ADR-24 en <<section-design-decisions>>
para el bug real que motivó esto). Sus resultados viajan en
`GeolocationOutcome.visual_inferences` (aficiones y texto visible, como
`InferredAttribute` normales, con su `confidence`/`evidence` igual que
las inferencias de texto), `GeolocationOutcome.partner_signal_permalinks`
(que `report/generator.py` usa para rellenar `estado_civil = "con_pareja"`,
`source = "imagen"`, solo si el texto no dio ya un estado civil) y
`GeolocationOutcome.visual_descriptions`/`general_descriptions` (la
descripción legible por foto que se muestra en el frontend, indexada por
el enlace específico de cada foto, no por el permalink de la publicación
-- ver ADR-23).

Degradación::
Igual que `geolocation.py`: si `torch`/`transformers` no están instalados
o la inferencia falla para una foto concreta, esa foto simplemente no
aporta señal (no rompe el resto del análisis). Igual que el modelo de
geolocalización, Moondream2 SÍ se precarga en el `lifespan` del
contenedor (ver `main.py`, condicionado a `ENABLE_SCENE_ANALYSIS`) --
ninguno de los dos espera a la primera foto real para cargarse.

Ubicación::
`backend/app/vision/scene_analysis.py`.

==== `report/generator.py`

Propósito/Responsabilidad::
Ensambla el `ExposureReport` final: fingerprint, atributos inferidos,
score, estrechamiento de población (k-anonimato, combinando regex + IA),
puntos de ubicación por imagen (si aplica, sin filtrar por confianza), y
recomendaciones generadas a partir de los umbrales del score. Las
recomendaciones se siguen calculando aquí igual que antes, pero ya no se
muestran como sección propia en el dashboard -- se usan como insumo del
análisis con IA (`ai_analysis.py`).

Aquí vive la decisión de CUÁNDO una geolocalización por imagen es lo
bastante fiable como para asumir residencia habitual (`_infer_home_region`):
antes bastaba una sola foto por encima de un umbral bajo (40% de
confianza), lo cual era demasiado alegre para un dato tan sensible. Ahora
exige consenso entre varias fotos de la MISMA comunidad autónoma:

* al menos 2 fotos con más del 80% de confianza (`HIGH_CONFIDENCE*`), o
* al menos 4 fotos con más del 60% (`MODERATE_CONFIDENCE*`, "muchas fotos
  aunque ninguna destaque individualmente").

Antes de contar votos se descartan las fotos marcadas como "de viaje"
(`nlp/travel_detection.py` + campo `fotos_de_viaje` de la IA) y las no
representativas (`ImageLocationEstimate.representative == False`, ver
`vision/geolocation.py`) -- ninguna de las dos cuenta como señal de
residencia, aunque ambas se siguen mostrando en el mapa con su confianza
real. Los umbrales (2/80%, 4/60%) son una primera propuesta razonable,
no una cifra derivada de ningún estudio; son constantes fácilmente
ajustables si en la práctica resultan demasiado (o poco) exigentes.

La jerarquía de fiabilidad para la ubicación final es: municipio > provincia
(texto/IA) > comunidad autónoma (texto/IA) > comunidad autónoma/provincia
por consenso de fotos. Es decir, si el texto ya dice "vivo en Canarias",
el consenso de fotos nunca lo pisa, por muy fuerte que sea la señal
fotográfica hacia otra zona.

El mismo criterio de "el texto manda si lo hay" se aplica a `estado_civil`:
si `ai_attribute_extraction.py` ya propuso uno por razonamiento simbólico
sobre el texto (`source = "ia_simbolica"`), ese se queda. Solo si el texto
no dio nada, y `vision/geolocation.py` devolvió al menos un
`partner_signal_permalinks` (señal de pareja detectada por
`vision/scene_analysis.py` en alguna foto), se rellena aquí con
`estado_civil = "con_pareja"` y `source = "imagen"` -- para que el
informe deje claro que, en ese caso concreto, la señal viene de una foto
y no de algo que la persona haya escrito.

Ubicación::
`backend/app/report/generator.py`.
